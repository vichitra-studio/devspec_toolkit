  DevSpec Toolkit: Automation & Improvement Strategy with Claude

  What This Toolkit Is (TL;DR)

  A 22-step waterfall pipeline (Steps 00→16c) that turns seed documents into
  validated, traceable specs and implementation. Each step has:
  - A JSON Schema defining the artifact shape
  - A deterministic prompt (prompts/prompt_NN_*.md) that instructs AI
  - A validation gate (schema + semantic linters)
  - Traceability links to upstream/downstream artifacts

  The AI workflow today is manual copy-paste: you read the prompt, feed it to an
   AI, get JSON back, write to disk, run validation. The agent protocol
  (docs/agents/manifest.json) defines a two-phase "Clarify → Emit" flow, but
  nothing enforces it programmatically.

  CLAUDE.md additions — encode the agent protocol directly:

  ## Spec Authoring Protocol
  When asked to work on a spec step:
  1. Read `spec/common/seed_manifest.json` first
  2. Read the step's prompt from `prompts/prompt_NN_*.md`
  3. Ingest all seeds listed in `step_requirements[NN]`
  4. Apply Self-Audit Gate: if confidence < 0.9, output bulleted questions ONLY
  5. When ready, write JSON to `spec/NN_name.json` (not fenced output)
  6. Run: `./tools/run_specdev.sh validate spec/NN_name.json --repo-root .`
  7. If validation fails, fix and re-validate (max 3 attempts)
  8. Run: `./tools/run_specdev.sh seed-lint spec --repo-root .`

  What This Review Phase Would Need

  Inputs:
  - The emitted artifact (just written to disk)
  - All upstream specs declared in step_order.json → required_spec_inputs
  - All seeds declared in seed_manifest.json → step_requirements[NN]

  Checks (5 dimensions):

  1. Upstream ID Coverage — For every ID in upstream specs that this step should
   consume: is it traced, or explicitly out-of-scope with rationale?
  2. Seed Distillation — For every requirement/constraint/persona in the seed
  docs: does some element in the output reflect it? (This is the hardest —

  5. Semantic Fidelity — The meaning was preserved through distillation. A
  charter goal about "sub-200ms response times" shouldn't become an NFR about
  "fast responses."

  ---
  The Token Problem: Quantified

  For a typical project with 10 FRs, 5 APIs, decent charter:

  ┌─────────────┬──────────────────────┬────────────┬──────────────┬───────┐
  │             │   Upstream specs     │  Tokens    │   Tokens     │       │
  │    Step     │        needed        │  ingested  │  actually    │ Waste │
  │             │                      │            │     used     │       │
  ├─────────────┼──────────────────────┼────────────┼──────────────┼───────┤
  │             │ Charter +            │            │              │       │
  │ 04 (FRs)    │ Capabilities +       │ ~5,000     │ ~1,200       │ 76%   │
  │             │ Glossary             │            │              │       │
  ├─────────────┼──────────────────────┼────────────┼──────────────┼───────┤
  │ 09 (Impl    │ 6 specs              │ ~10,000    │ ~3,000       │ 70%   │
  │ Plan)       │                      │            │              │       │
  ├─────────────┼──────────────────────┼────────────┼──────────────┼───────┤
  │ 16a         │ 5 specs + roadmap    │ ~15,000    │ ~4,000       │ 73%   │
  │ (Planner)   │                      │            │              │       │
  └─────────────┴──────────────────────┴────────────┴──────────────┴───────┘

  And that's per step. Across a full pipeline: ~59k tokens ingested, ~19k
  actually needed. 40k tokens wasted.

  The root cause: extraction_intent in step_order.json tells you exactly which
  fields each step needs — but nothing enforces it. The AI reads entire
  1500-line specs when it needs 3 fields.

  ---
  Three-Layer Optimization Strategy

  Layer 1: Spec Projection (Mechanical — biggest win)

  Build a specdev project command that slices specs before they reach Claude:

  step_order.json says step 04 needs from charter:
    "Extract goals and constraints for FR rationale"
                      ↓
  Project charter to only { goals, constraints, in_scope, out_of_scope }
                      ↓
  Feed 700 tokens instead of 3,400

  How it works:

  extraction_intent (natural language)
          ↓
  field_map.json (new file, machine-readable)
          ↓
  specdev project --for-step 04 --output /tmp/context/
          ↓
  Projected specs written to temp dir
          ↓
  Claude ingests projected specs only

  The new field_map.json would formalize extraction intent:

  {
    "04": {
      "00_charter.json": ["goals", "constraints", "in_scope", "out_of_scope"],
      "01_capabilities.json": ["capabilities[].capability_id",
  "capabilities[].scope"],
      "03_glossary.json": ["terms[].term", "terms[].definition"]
    },
    "09": {
      "00_charter.json": ["goals", "constraints", "risks"],
      "01_capabilities.json": ["capabilities[].capability_id",
  "capabilities[].approved_tech"],
      "04_functional_requirements.json": ["functional_requirements[].fr_id",
  "functional_requirements[].statement",
  "functional_requirements[].acceptance_criteria"]
    }
  }

  Impact: 60-75% token reduction per step.

  Layer 2: Tiered Ingestion (Architectural)

  Not all context is needed at the same depth. Structure ingestion in tiers:

  Tier 0 — IDs only          (~5% of tokens)
    Just the IDs and names from upstream specs.
    Used for: traceability binding, reference validation

  Tier 1 — Summaries          (~15% of tokens)
    IDs + one-line statements/descriptions.
    Used for: FR-to-capability mapping, scope checking

  Tier 2 — Projected fields   (~30% of tokens)
    Fields specified by extraction_intent.
    Used for: actual spec authoring

  Tier 3 — Full spec          (~100% of tokens)
    Complete JSON.
    Used for: ONLY when reviewing/auditing completeness

  How Claude uses tiers in practice:

  /spec-step 04

  1. Load Tier 0 of all upstream specs (IDs only)     → ~500 tokens
  2. Load Tier 2 of required specs (projected fields)  → ~1,200 tokens
  3. Load seeds in full (they're small prose docs)      → ~800 tokens
  4. Load the prompt contract                           → ~2,000 tokens
                                                         ─────────────
                                                Total:    ~4,500 tokens

  vs. today: ~12,000+ tokens

  Tier 3 (full spec) is reserved only for the review phase — when Claude needs
  to verify nothing was dropped. And even then, it can be done one spec at a
  time rather than all at once.

  Layer 3: Index-First Architecture (Long-term)

  Build a spec index that Claude queries on demand instead of loading everything
   upfront:

  spec_index.json (auto-generated, lightweight)
  ├── ids: { "fr-user-login": { step: "04", line: 42, statement: "..." } }
  ├── traces: { "fr-user-login" → ["cap-auth", "goal-secure-access"] }
  ├── coverage: { "cap-auth" → ["fr-user-login", "fr-sso-oauth"] }
  └── canonicals: { "cn:action:create" → ["fr-user-login", "api-session-create"]
   }

  Claude reads the index (~2k tokens), identifies what it needs, then reads only
   the specific sections using line offsets. This is how the Read tool already
  works — you can read specific line ranges.

  The reviewer.py Implementation

  The automated part needs these capabilities:

  # tools/specdev_tools/context/reviewer.py

  class ReviewPair:
      check_type: str          # faithfulness | acceptance_gap | 
  seed_distillation | quantifier_weakening
      source: SourceRef        # {id, file, path, text}
      target: TargetRef        # {id, file, path, text}  
      concern: str             # heuristic-generated hint

  class ReviewResult:
      structural: StructuralReview     # ID coverage, reverse trace, AC coverage
      semantic_pairs: list[ReviewPair] # pairs for LLM judgment
      verdict: str                     # PASS | NEEDS_SEMANTIC_REVIEW | FAIL

  def review(artifact_path, step, entry_id, spec_dir, repo_root) -> 
  ReviewResult:
      # 1. Run structural review (existing traceability_closure + matrix logic)
      # 2. Generate semantic pairs:
      #    a. For each covered ID: extract source text + target text → 
  faithfulness pair
      #    b. For each missing AC: find nearest checklist match → acceptance_gap
   pair  
      #    c. For each seed requirement in scope: grep for distillation → seed 
  pair
      #    d. For each source with numbers: check target for vague words → 
  quantifier pair
      # 3. Return structured result

  The heuristics for generating concern strings:

  - Faithfulness: extract nouns from source, check which are missing from target
  - Seed distillation: extract key terms from seed excerpt (PCI-DSS, tokenized,
  Level 1), check if target contains them
  - Quantifier weakening: regex \d+\s*(ms|seconds|s|%|MB|GB|req/s) in source,
  check if target has fast|quick|acceptable|reasonable|adequate instead

  These are cheap string operations. No LLM needed for pair generation — only
  for final judgment.

      "req_id": "seedreq-pci-dss",
      "text": "All payment processing must comply with PCI-DSS Level 1"
    },
    "target": {
      "id": "inv-payment-compliance",
      "text": "Payment processing must follow PCI-DSS requirements"
    },
    "concern": "Source specifies 'Level 1', target says generic 'requirements'. 
  Compliance level dropped."
  }

  The heuristic for generating concerns: extract specificity markers (numbers,
  levels, proper nouns, acronyms with qualifiers) from source and check if
  target preserves them.

  How index-seeds Works (the LLM step)

  This is a one-time cost per seed document. The prompt is tight:

  Read this seed document. Extract every discrete system requirement
  as a separate entry. A "requirement" is any statement that:
  - Constrains what the system MUST or MUST NOT do
  - Specifies a measurable quality attribute (latency, uptime, etc.)
  - Mandates compliance with a standard or regulation
  - Defines a user-facing behavior expectation

  For each requirement:
  1. req_id: kebab-case identifier (prefix: seedreq-)
  2. text: exact or minimally normalized quote
  3. section: which markdown heading it falls under
  4. line_range: [start_line, end_line]
  5. category: one of [fr, nfr, security, compliance, api, data, ux, ops]
  6. expected_steps: which pipeline steps should address this

  Write to spec/common/seed_requirements.json

  Cost: ~2,000 tokens per seed document. Happens once. Not per step.

  Staleness Detection

  When a seed doc changes, the index is stale:

  specdev context check-seed-freshness spec/ --repo-root .

  # Output:
  {
    "seed-overview": {
      "indexed_hash": "sha256:abc123...",
      "current_hash": "sha256:def456...",
      "stale": true,
      "changed_lines": [7, 8, 14, 15],
      "affected_requirements": ["seedreq-search-latency", "seedreq-new-unknown"]
    }
  }

  This can be a pre-commit hook or part of seed-lint. If stale, the skill
  re-runs index-seeds on only the changed sections.

  SEED AUTHORING (one-time per seed change)
  ───────────────────────────────────────────
  1. Human writes/updates docs/seed/seed_overview.md

  7.1 Findings

  Analysis of seed templates and pipeline seed propagation revealed three
  structural issues:

  a) Web-app bias: Both seed templates (seed_overview.md, seed_tech_stack.md)
     hardcoded web-app concepts (Frontend/Backend/Database layers, WAF/Firewall,
     Deploy to Dev/Stage/Prod), making them unusable for libraries, frameworks,

  b) Unnecessary seed propagation: All 22 pipeline steps were told to read raw
     seed documents, even though Steps 00-04 already distill all seed content
     into structured JSON specs. Steps 05+ work entirely from upstream specs
     and should use the Clarify-Emit protocol for any gaps.

  c) Content overlap: seed_overview.md sections 4.2 (NFRs), 4.3 (Security),

     creating conflicting sources of truth.

  7.2 Design Decisions

  D1: Pipeline Role Model — Seeds feed Steps 00-04 only. Steps 05+ derive
      from structured specs and use Clarify-Emit for gaps. Seeds never flow
      past Step 04.

  D2: Seed Ownership Boundary — seed_overview owns product intent (problem,
      users, scenarios, success metrics, scope, domain model, timeline, team).
      seed_tech_stack owns technical decisions (system type, technology choices,
      architecture, components, security boundary, distribution, resilience,
      dependencies). No overlap.

  D3: Seeds Are Not System Specs — Seeds capture design intent accessible to
      non-developers. Detailed technical decisions are discovered by pipeline
      steps, not pre-specified in seeds.

  D4: Drop seed_indexer and seed_reviewer — The original build plan proposed
      these modules for the context package. They are redundant: the existing
      seed_manifest system handles discovery, pipeline steps distill seeds,
      and seed-lint validates references.

  D5: [UNKNOWN] Protocol — Templates introduce [UNKNOWN: reason] as a
      sanctioned marker for genuinely unknown information, replacing the
      "remove all TBDs" instruction that pressured fabrication.

  D6: System-Type Agnostic Templates — Templates work for any software type
      with no hardcoded architecture layers, deployment models, or
      web-specific security.
