## [1.2.0]

### Breaking Changes

- Steps 00 to 05 move to the spec-graph shape; existing host specs do not validate until migrated (`specdev align apply <spec> --auto` migrates them; the migration scripts of this release are listed under Added). Step 00: `in_scope` / `out_of_scope` merge into `scope_items` (each with `scope` `in` | `later` | `out`, `scope_reason` for `later` / `out`, `scope_id`), and the 1.1.1 floor of three entries in each of the two lists becomes one entry in `scope_items`; assumptions, risks and stakeholder needs become objects with ids (they were strings), stakeholders gain `stakeholder_id`, new `constraints` list, `links` removed, `derives_from` added to scope items, assumptions, risks, needs, segments, metrics and constraints. Step 01: capabilities lose `goal_id`, `success_metric_refs` and `trace` and gain `derives_from` and `scope_reason`; the `scope` value `future` becomes `later`. Step 02: components and connections lose `trace`; component `type: external` and the tag `external-dependency` removed (model the service as a `third_parties` entry); connections lose `from`, `to`, `schema_ref` and `interface_ref` and gain `connection_id`, `derives_from` (source) and `connects_to`; new `third_parties` (`tech_stack` removed). Step 02a: artifact-level `trace` removed; `ci_gates` and `secrets` become objects (`gate_id`, `secret_id`); each environment gains `scope`, `derives_from` and a `config` object that holds the host keys. Step 03: terms gain `aliases`, `lifecycle`, `replaces`. Step 04: FRs lose `trace` and gain `derives_from` (capabilities) and `depends_on` (FRs); acceptance criteria gain `scope`. Step 05: APIs lose `trace` and `example_refs` and gain `derives_from` (FRs), `provided_by`, `relies_on` and `depends_on`; each error gains required `error_id`, `scope` and `derives_from`. `scope` (`in` | `later` | `out`) becomes required on every functional requirement, API, API error, acceptance criterion, charter risk, environment, CI gate and secret; none of them had it in 1.1.1 (capabilities already required it). `scope_reason` is required wherever `scope` is `later` or `out`, capabilities included (1.1.1 had no such rule). `derives_from` with at least one id becomes required on every node of steps 00 to 05 except stakeholders, glossary terms and acceptance criteria. A stakeholder needs at least one need. Every node accepts `aliases`, `lifecycle` and `replaces`; every node except an assumption and a glossary term also accepts `assumes`.  `specdev align status` / `diff` / `plan` report nothing for a 1.1.1 spec of steps 00 to 05 against the new schemas, top-level renames such as `in_scope` to `scope_items` included, because the differ reads only a schema's own top-level `required`, `properties` and `additionalProperties`, and these step schemas keep their properties under `allOf`.
- Link-existence checks are removed from the step validators of 01 (capability to component), 02 (connection endpoints) and 05 (API to requirement, with its W590 for a missing step 04 file). They are replaced by the `graph` check of `spec-check` (E700 to E703); a single-file `specdev validate` of those files does not report a link to an id no node has. The step 04 check that a requirement carries a non-empty `trace` and the step 02 check for a missing `tech_stack` go with those fields. The step 02 capability-coverage check (E590) stays; it now reads component `derives_from` and exempts capabilities whose `scope` is `later` or `out`. Other content checks stay, for example the duplicate method and route check of step 05 (E520). Three validator modules are deleted: `validation/validators/step_01.py` (the capability-to-component check), `validation/validators/step_02a.py` (an E520 for a duplicate `ci_gates` entry; a gate is a node with a `gate_id`, and a duplicate id is E704) and `validation/validators/step_16b.py` (E520 checks of `execution.execution_results`, a removed plan field; a plan file is checked by the 16a and 16c validators).
- A check that reads fields of the 1.1.1 shape (`trace`, `goal_id`, `success_metric_refs`) runs only when the files it reads carry those fields. A 1.1.1 spec whose step-05 APIs carry no `trace` at all is invalid under the 1.1.1 schema. The step-11 W583 check reads API `derives_from`: a 1.1.1 step-05 API linked only to parked requirements through `trace` is no longer exempt from W583. The closure checks (E535, E560, W564, W568), the matrix coverage warning (W592, E592), `completeness-check` and `specdev matrix`, which this entry described for a spec in the new shape, are removed in this release (see the entries on the retired closure and completeness checks and on the retired matrix).
- Steps 06 to 16 move to the spec-graph shape, with the core schemas they share; existing host specs do not validate until migrated. `specdev align apply <spec> --auto` migrates a 1.1.1 spec to this shape (the migration scripts of this release are listed under Added), but `specdev align status` / `diff` / `plan` read only a schema's own top-level `required`, `properties` and `additionalProperties`, while the step schemas keep most or all of their properties under `allOf`, so they miss the changes below, top-level ones included (`align diff` reports a 1.1.1 file of step 07, 08, 11 or 14 as `OK`). The module `migration/planner.py`, which ordered such differences into a plan of template steps, is deleted; `align apply --auto` runs the migration scripts of `migration/scripts/v1_2_0/`. `specdev update` does not rely on that comparison alone: it does not re-stamp `spec/specdev_version` on a spec that needs a migration, and prints the commands to run instead.
- Core and every step schema: `spec_refs_ingested` and `seed_refs_ingested` are removed from steps 00 to 16 (`16_anchor` and `16_impl_context` included) and from `core/step_base`, with the definitions `specRefIngested*` and `seedRef*`. Steps 00 to 15 gain an optional top-level `ambiguities` list of open items: each item has `id`, `description` and `about` (ids it concerns), and optional `missing_kind`, `decision` and `proposed_assumption`; it has no other field. `plan.ambiguities` in `16_anchor` and `16_impl_context`, and `execution.emergent_ambiguities` in `16_impl_context`, use the same open item: `severity`, `status`, `impact` and `resolved` are removed (and `source` and `mitigation` from `plan.ambiguities` of `16_impl_context`), and `about` is required. The core definitions `crossCycleAmbiguityItem` and `ambiguityStatus` are removed. `testingMode` and step 08 `fixtures[].mode` gain the value `manual`. The core definitions `dependencyList`, `techStack`, `techStackItem`, `techStackList`, `dependencyItem`, `dependencyObjectList`, `link`, `httpMethodFull`, `traceRef` and `traceId` are removed with their last use.
- Steps 02, 04 and 05 (finishing the step 00 to 05 change above): `tech_stack` is removed from step 02 (use `third_parties[]`); the `priority` value `wont-have` is removed from step 04 functional requirements (use `scope: later` or `scope: out`); the top-level `out_of_scope` list is removed from step 05 (mark the requirement `scope: out` with a `scope_reason`).
- Steps 06 and 07: `rules[].trace` (step 06) and `nfrs[].trace` (step 07) are replaced by `constrains`, an optional list of ids of functional requirements, APIs, components or connections. Step 06 `rules[].scope`, an object `{components, apis}` in 1.1.1, becomes the string `in` | `later` | `out` (default `in`; `later` and `out` need `scope_reason`). Step 07 gains optional `relies_on` (third parties), `derives_from` (metrics) and `scope` / `scope_reason`. Both steps gain optional `assumes`, `lifecycle`, `aliases` and `replaces` on every node. The node kind of step 06 is `invariant`.
- Step 08: `fixtures[].targets` is replaced by `verifies` (ids of acceptance criteria, APIs, invariants or NFRs; not FRs), and the top-level `out_of_scope` list is removed. A fixture needs `verifies` or `removes`. New optional `manual_reason` (a string of at least 10 characters), required when `mode` is `manual`. Fixtures gain `lifecycle`, `aliases` and `replaces`.
- Step 09: the top-level `tech_stack`, `tech_stack_ref`, `trace`, `dependencies` and `dependency_ref` are removed, and `milestones` is the step's own required top-level field (the step-base fields `id`, `owner`, `created_at` and `canonical_refs_used` stay required). Each milestone loses `status`, `deliverables` and `depends_on` and requires `schedules` (at least one id of a functional requirement, acceptance criterion, API, invariant, NFR, component, environment or risk); it gains `lifecycle`, `aliases` and `replaces`. The node kind is `design-milestone`.
- Step 10: `pr_rules`, `spec_first_policy`, `review_policy`, `reviewers`, `trace` and `links` are removed. `rules` (at least one) is required beside `commit_message_rules`. Each rule (node kind `rule`) needs `rule_id`, `text` and `derives_from` (at least one id of a constraint, risk, scope item, gate, environment or stakeholder), and may carry `enforcer` (only `review`), `cli_command`, `assumes`, `scope`, `scope_reason`, `lifecycle`, `aliases` and `replaces`; a rule with `enforcer` must not carry `cli_command`. `versioning`, `policy_ref` and `command_ref` stay. A rule's `cli_command` must be a command of `tools/cli_commands.json`; any other value is E530 at step 10, owned by step 10.
- Step 11: the artifact-level `trace` is removed. A threat's `target_ids` becomes `threatens` (required, at least one id of an API, component, connection or third party) and `mitigations` becomes `mitigated_by` (optional ids of functional requirements, criteria, APIs, API errors, invariants, NFRs, rules, gates, secrets, environments, constraints or fixtures); a threat gains optional `derives_from` (risks). An edge case now requires `threatens` (APIs, components or FRs) and `mitigated_by` (at least one id). Threats and edge cases gain `scope`, `scope_reason`, `assumes`, `lifecycle`, `aliases` and `replaces`. The node kinds are `threat` and `edge-case`.
- Step 12: `trace` is removed. `jobs[].requires` is renamed `jobs[].depends_on` (ids of jobs of the same file), and `jobs[].steps[].id` is removed (a step needs `name` and `command`). Jobs gain optional `realises` (environments, gates, secrets or rules), `verifies` (NFRs), `lifecycle`, `aliases` and `replaces`. The node kind is `job`.
- Step 14: the top-level `tech_stack`, `tech_stack_ref`, `dependencies`, `dependency_ref` and `trace` are removed. A milestone loses `status`, `milestone_status_reason`, `source_milestones`, `fr_refs`, `capability_refs` and `deliverables`, and requires `milestone_id`, `name`, `target_date`, `user_story` and `tasks` (node kind `roadmap-milestone`). A task loses `status`, `status_reason`, `assumptions`, `exit_conditions`, `fr_refs` and `invariant_refs`; its `depends_on` items are kebab-case task ids; it gains `disposition` (`value`: `deferred` or `wont_do`, and `reason`, both required) to set a task aside (node kind `task`). An acceptance criterion's `fixture_ref` is renamed `verified_by` (ids of fixtures, jobs or rules), and the criterion needs `refines` (at least one id of an upstream node) or `removes` (at least one id) (node kind `task-criterion`). Milestones, tasks and criteria gain `lifecycle`, `aliases` and `replaces`.
- Step 15: `trace` and `links` are removed. Each `interface_map[]` row loses `interface_ref` and `method` and requires `row_id` (a kebab-case id), `realises` (at least one API id) and `path`; an API may be realised by several rows. Rows gain `lifecycle`, `aliases` and `replaces`. The node kind is `scaffold-row`. `project_skeleton`, `validators`, `command_ref` and `build_status` stay.
- Step 16 anchor (`16_anchor`): each `plan.milestone_index[]` row loses `milestone_id`, `context_path` and `fr_refs`. A row requires `anchor_id`, `about` (the id of one roadmap milestone), `checklist_id_prefix` and `summary`; `status` stays and is optional, and an absent `status` reads as `pending`. `deferral_reason` is required when `status` is `deferred`; `close` (`signed_off_by`, and `source` when `signed_off_by` is `legacy-migration`) is required when `status` is `done`. The node kind is `anchor-row`.
- Step 16 plan (`16_impl_context`): the file requires a file-level `milestone` (the roadmap milestone id the plan is about), and the anchor validator finds the plan of an anchor row through it (`milestone-state` still finds a plan by its file name). A plan is a file `impl_context/ms_<batch>_plan.json`: another JSON file in that folder is no plan. `plan.status`, `plan.deferred_reason` and `plan.coverage_status` are removed. A plan item (`plan.spec_alignment.checklist[]`, node kind `plan-item`) loses `spec_ref`, `milestone_ref`, `nfr_refs`, `fixture_ref`, `checklist_status`, `deferred_reason`, `wont_do_reason`, `linked_test_expectation` and `implementation.status`; it requires `id`, `realises` (at least one task-criterion id), `description` and `implementation`, and gains `lifecycle`, `aliases` and `replaces`. Also removed: `plan.spec_alignment.requirements_summary[].spec_refs`, `plan.security.new_fixtures`, `plan.security.spec_mutations`, `execution.critical_evidence`, `execution.execution_results[].evidence_binding`, `review.fixture_status.test_results` and `extensions.review_state`; `review.findings[].spec_ref` loses `line_range` and `commit_hash`; `review.fixture_status.implemented_interfaces[]` items are plain kebab-case ids. A passed `execution.execution_results[]` entry no longer needs `evidence_binding` beside `evidence_ref`.
- The replay check is removed. `specdev forward-replay-check` exits 2 and prints "specdev: forward-replay-check was removed in 1.2.0; use `specdev stale` for the pending replay and `specdev spec-check` for broken links"; `spec-check --include-forward-replay` is an argument error (`unrecognized arguments: --include-forward-replay`, exit 2); `validate-all` runs no replay step and prints no "skipped" line. The environment variable `SPECDEV_REPLAY_DIFF_ERROR_MODE` is no longer read (`specdev env-check` lists any `SPECDEV_*` variable that is set, but nothing reads this one); `SPECDEV_REPLAY_BASE_REF` stays and names the base ref of the step gate and of `specdev diff`. The keys `policy.require_full_forward_replay_on_change` and `policy.status_write_exemptions` are removed from `tools/step_order.json`, and `schema/step_order.schema.json` allows no other key in `policy` (`additionalProperties: false`). The codes E550, W550, E555 and W598 (id regression and replay diff), W560 (a relabelled closure gap), W140 (seed content overlap) and W551 (a seed on disk that the manifest does not declare) are removed from the registry and the catalogue (`specdev guide E555` prints `no remediation guide for E555`). What answers the same question: a deleted node is a broken link at each node that links it (E700, E701, owned by the step of the holder; `specdev spec-check`); a changed upstream node is a suspect link (E763; `specdev stale`, then `specdev attest`); a seed that no route names or no node of its step uses is E747, E748 or E749. A host must delete the CI lines that call `forward-replay-check` or pass `--include-forward-replay` (both now exit 2) and unset `SPECDEV_REPLAY_DIFF_ERROR_MODE`.
- Step 13a (the completeness assessment) is removed: its prompt `prompts/prompt_13a_completeness_assessment.md`, its schema `vc:13a-completeness-assessment`, its validator, the migration template `prompts/migration/template_completeness_assessment.md`, its entry in `tools/step_order.json` and `tools/step_docs.json`, and the canon kind `completeness_dimension` (the kind file, the four entries `cn:core:completeness_dimension:ambiguity`, `:completeness`, `:quality` and `:traceability` of `canon/manifest.json`, and the autofix rule that mapped `category` to `completeness_dimension_ref`). `specdev prompt-context 13a` prints `Error: Unknown step '13a'`; `spec-check --step 13a`, `step ready 13a` and `step create 13a` print `E706 no step '13a'; known steps: 00, 01, 02, 02a, 03, 04, 05, 06, 07, 08, 09, 10, 11, 12, 13, 14, 15, 16, 16a, 16b, 16c`. `step ready 14` and `step ready 16a` no longer wait for a 13a file. What answers the same question: `specdev coverage` (the link counts and the ids that are not linked), the role findings E740 to E745 of `specdev spec-check`, and `specdev step ready 14`, which lists the blockers owned by the steps below 14 (on a copy of the worked example with steps 14 to 16 removed: 11 blockers at steps 07, 08 and 12); the gaps that step 14 owns (E566, E742, E744, E745 and the E740 of the nodes a task criterion uses) are not blockers, and the task criteria of step 14 clear them. A host must delete its `spec/13a_completeness_assessment.json`: left in place it gives E520 `schema_not_found uri=vc:13a-completeness-assessment` from `spec-check` and `validate-all` (run on a copy of the worked example with such a file). A project canon entry of kind `completeness_dimension` does nothing now (on a copy of the worked example with one added, `spec-check` reported the same findings and `canonical-lint` printed `OK`); delete it. `specdev align apply --auto` migrates both (`p3_remove` deletes the file, `p3_host_canon` the canon kind).
- The closure and completeness checks are removed. `specdev completeness-check` exits 2 and prints "specdev: completeness-check was removed in 1.2.0; use `specdev coverage` for the link counts and the ids that are not linked"; `specdev traceability-check` exits 2 and prints "specdev: traceability-check was removed in 1.2.0; use `specdev spec-check` for the role-rule findings (E740 to E745) and broken links". The `spec-check` checks `traceability-closure` and `completeness-check` are gone from the summary, and `validate-all` no longer raises E535, E536 or E560. The module `validation/traceability_closure.py` is deleted. The codes E535, E536, E560, E561, E562, E563, E564, E565, E568, E569, E575, E576, W561, W562, W563, W564, W565, W568, W569, W575 and W576 are removed from the registry and the catalogue; together with the codes of the matrix entry below, the promotable pairs go from 23 to 10. The question each closure code asked is now a role rule or a link check: a node that nothing uses is E740, a missing fixture or verifier is E742 or E743, a link to an id no node has is E700 or E701, and an FR that no task criterion reaches is E566 (see the step 14 entry). `specdev context freshness` no longer writes W595 (`CONTENT_STALENESS`, `SEED_UNTRACKED`) to stderr and no longer exits 1 under `SPECDEV_WARNINGS_AS_ERRORS`; its JSON keeps the keys `stale` and `untracked`. A seed that changed is a suspect link (`specdev stale`); a seed that no node links has no signal in the graph (E747 to E749 are other conditions: a seed no route names, a route no node uses, a link to a seed the route does not reach). W595 stays registered for the messages of `specdev seed-index`. `specdev extraction-intent-check` now reads a `## Extraction Intent` section too (it skipped eight prompts before); an empty seed file is still not reported. A host must delete the CI lines that call either command (both now exit 2).
- The trace matrix and the trace types are removed. `specdev matrix` exits 2 and prints "specdev: matrix was removed in 1.2.0; use `specdev coverage --by fr` for the FR view and `specdev trace --up|--down <id>` for lineage"; its `--out` and `--json` flags go with it. No command writes `spec/extras/trace_matrix.json` now, and nothing reads it (a leftover copy gives no finding in `spec-check`). The environment variable `SPECDEV_MATRIX_STRICT` is no longer read, and `specdev env-check` no longer prints the lines `Coverage thresholds` and `Matrix strict mode`. `coverage_thresholds` is removed from `tools/step_order.json` and from `schema/step_order.schema.json` (it was required). The codes E604, W604 (`TRACE_MATRIX_STALE`), E592 and W592 (`COVERAGE_THRESHOLD_*`) are removed: `SPECDEV_PROMOTE_CODES=W592` prints "specdev: SPECDEV_PROMOTE_CODES contains unrecognised code 'W592'; it will be ignored." The canon kind `trace_type` is removed (the kind file and its 11 entries `cn:core:trace_type:*` of `canon/manifest.json`), with the modules `core/trace_types.py`, `validation/matrix.py` and `validation/cross_artifact_checks.py` and the lazy aliases `specdev_tools.trace_types` and `specdev_tools.matrix`; `hallucination-lint` no longer reports E530 for an invented `type` in a `trace` entry. The CI workflow that `init` used to generate had a "Build trace matrix" and an "Upload matrix" step; `init` no longer writes that workflow, the merge-check workflow that `specdev update` installs has neither, and `.gitignore` no longer lists `tools/trace_matrix.json`. What answers the same question: `specdev coverage`, `specdev coverage --by fr` and `specdev trace`. A host must delete the CI lines that call `specdev matrix` (now exit 2; `specdev update` reports each as W932), may delete a leftover `spec/extras/trace_matrix.json`, and should unset `SPECDEV_MATRIX_STRICT`.
- Step 16 plan (`16_impl_context`), breaking for a host's plans: the action `id` is required (`a01`, `a02`, ...), and the 1.1.1 plan fields that the new loop replaces are removed: `execution.execution_results`, `execution.final_status`, an action's `evidence`, `review.fixture_status`, `review.semantic_review.fr_coverage` and the two `verified` conditions of the review block. A host plan with an action that has no `id`, or with a removed field, is reported by `specdev spec-check` and `specdev validate` as `E520` (`'id' is a required property`; `Additional properties are not allowed`); the plan of a milestone closed by a migration (a `close` whose `signed_off_by` is `legacy-migration`) is exempt. `specdev align apply --auto` adds the action ids and the plan's `milestone` key (`p2_action_ids`, `p2_plan_milestone_key`); until it has run, a 1.1.1 plan is read only through `specdev status` and is not driven through `/specdev-trinity`. Shown by `specdev spec-check spec --repo-root ./devspec_toolkit --spec-root ./spec --git-root .`.
- Step 13: an extension is an entry of the manifest and two files in `spec/extensions/`, and each entry requires `justified_by`. The files are `ext_NN_<topic>.schema.json` (the host's JSON Schema, draft 2020-12, `$id` `vc:ext-NN-<topic>`) and `ext_NN_<topic>.json` (its data, `$schema` the same URI). An entry with no schema file or no data file is `E520`, and so is a JSON file of that folder that no entry declares. A data file left at the 1.1.1 place (`spec/ext_NN_<topic>.json`) is `E520` `schema_uri_mismatch` with the place to move it to. `justified_by` lists at least one component, third party, capability, FR or NFR that makes the extension necessary: `specdev align apply --auto` leaves the entry as it was, `specdev spec-check --step 13` reports it (`'justified_by' is a required property`), `specdev align propose --kind prose-ids` proposes the ids the `justification` names, and `specdev json patch --id <extension-id> .justified_by '["<node-id>"]'` writes the field with its lock entries. An open item in the `ambiguities` list of a data file is counted as an open item of step 13 (`W630` at the step gate, `E631` at the merge gate). A host whose manifest says `extension_decision.status: none-required` sees no change. The steps: `docs/developers/workflows/workflow_migrate_1_2_0.md`, "Step 13: the files and the links of an extension".
- Step 13: `required_schema_sections` of an extension holds at least 3 names (`minItems` 3, the ">=3 dedicated schema sections" of the prompt). A 1.1.1 extension with fewer is `E520` from `align validate`; add sections, or remove the extension (`specdev json delete --id <extension-id>`; when it is the only extension, remove it and set `extension_decision.status` to `none-required` in one `specdev json patch <file> --batch`, since either alone is refused).
- Step 14: a milestone with `risk_status` `high` or `critical` needs at least one entry in `risks`. A 1.1.1 milestone without one is `E520` from `align validate`; add a risk (`specdev json patch --id <milestone-id> .risks '["<risk>"]'`; `json insert` is refused when the milestone has no `risks` key) or lower `risk_status`. The `target_date` description now says what the validator checks: non-decreasing order, equal dates allowed.
- Step 06: `severity` is required on every rule (the schema description said so, the `required` list did not; `rules[].required` gains `severity`). A 1.1.1 rule without it is `E520` from `align validate`; set it with `specdev json patch --id <inv-id> .severity '"error"'`. Which rules are `error` stays an authoring and review rule that no tool checks (prompt 06).
- Step 10: `commit_message_rules.pattern` is required when `require_spec_ids` is `true` (an if / then in the schema). A 1.1.1 file with `require_spec_ids: true` and no pattern is `E520` from `align validate`; add the pattern with `specdev json patch spec/10_governance.json .commit_message_rules.pattern '"<regex>"'`, or set `require_spec_ids` to `false`. A pattern that is not a valid regular expression makes `governance-check` report `E303 commit_message_rules.pattern is not a valid regular expression: <reason>` (it ended in a traceback).
- Step 05: `path` and `method` are required when `protocol` is `http` (an `if`/`then` of `apis[]`; the descriptions said they were optional). A 1.1.1 `http` API without either is `E520` from `align validate`; set them with `specdev json patch --id <api-id> .path '"/..."'` and `.method '"GET"'`. An API of another protocol needs neither.

### Added

- `schema/core/graph.schema.json` (`vc:core:graph`): the `x-node` / `x-link` annotation language for declaring graph nodes and links in step schemas. See `docs/developers/schema-annotations.md`. The seed manifest (`schema/seed_manifest.schema.json`) and the step schemas 00, 01, 02, 02a, 03, 04 and 05 are annotated; the schemas of steps 06 to 12, 14, 15 and 16 are annotated too; the schema of step 13 declares the `extension` kind and gets the shared `ambiguity-item` node through the core `ambiguityList`.

- The trace lock `spec/extras/trace.lock.json` (`$schema` `vc:extras:trace-lock`, `schema/extras/trace_lock.schema.json`) holds one entry for each link of the spec: the holder, the field, the target, and the content hash and chain stamp (`sha256:` and 64 hex digits) the target had when the holder accepted the link. A link whose target now has another chain stamp is a suspect link (E763); the cause is `content_changed` (the target was edited) or `upstream_changed` (a node above it was). Links held by the nodes of a closed milestone (an anchor row with status `done`) are not suspect and cannot be re-attested (E765). The worked example carries a lock of 64 entries. - `specdev lock merge BASE OURS THEIRS PATH` is a git merge driver for the lock: it merges the three versions entry by entry and writes the result over OURS (E760 for an input that is not a valid lock, E520 for a file that cannot be read); when both sides changed one entry in different ways it keeps the entry the common ancestor had, or, when it had none, the entry with the smaller chain stamp (string order), and the link is suspect again when its target changed after the kept entry. `specdev lock install-driver --driver-command CMD` adds the line `<path of the lock relative to the git top level> merge=specdev-trace-lock` (`sub/spec/extras/trace.lock.json merge=specdev-trace-lock` for a spec folder `sub/spec`) to the file `git rev-parse --git-path info/attributes` names and sets `merge.specdev-trace-lock.driver` to `CMD %O %A %B %P` in the clone at the git root (`--git-root`, or the folder that holds `--spec-root`); running it again changes nothing. `specdev update` (and `init`, which runs it) installs the driver in the clone it runs in, with the command `<venv>/bin/specdev lock merge`: run it once in each clone, otherwise git merges the lock as text, and a conflict leaves conflict markers in it, which `specdev` reports as E760 with the repair.

- `specdev spec-check` gates one step: `--step N` (repeat it for several steps; a step given twice is gated once) blocks on the errors that step N owns and on errors of earlier steps that are new since the baseline; `--paths FILE...` (every word up to the next option; zero or more files; write `spec_dir` before it) gates the steps of the files you list; `--base-ref REF` (default: `SPECDEV_REPLAY_BASE_REF`, `origin/HEAD`, `origin/main`, `origin/master`, `main`, `master`) names the base ref, and the baseline is its merge-base with `HEAD`; `--detail {summary,all}` lists upstream debt, pending (owned by a later step) and gate-owned findings in full. The report goes to stdout and notes to stderr, and the exit code is 1 only when the result is BLOCKED, with `--json` too. A new error is told from an old one by the key (code, owner, node id, link target, file, location, subcode, path; the location is the jq path with the array indexes removed, except an index inside a quoted key, which is part of the key), never by its message, and by count: for each key, a finding is new only when the working tree has more findings with it than the baseline had. A reworded message, or an item inserted before an old error, is not new. One limit: an error fixed and another of the same key (the same code, file and place, array indexes aside) added on the same branch reads as no change at the step gate; plain `spec-check` lists the new one, and the merge check (`specdev spec-check --merge`) reports every error. An error fixed in one file or place does not offset a new error in another. A schema error (E520) of `spec-check --json` now carries `file` (relative to the spec folder) and `jq_path`, and `validate` and `validate-all` `--json` give `jq_path` on E520 (a key that is not a name in jq is written in brackets: `.step_requirements["00"]`); the where column of the step gate text shows that file name where it showed `-`. With several steps each bucket of the `--json` report is the union over the steps. When no baseline can be used the report says `base: unavailable`, every upstream error counts as new, and stderr gives the reason; a branch that adds the spec folder, such as a host's first adoption branch (or a base commit that holds a file named like the spec folder), gets `the spec folder is not in the base commit <12-char sha>: every error of an earlier step counts as new`. With `--step` or `--paths`, a spec folder that does not exist, a toolkit with no readable `tools/error_ownership.json`, and a toolkit whose `tools/step_order.json` is unreadable (`E520 <path> step order is unreadable: <reason>`, for a missing file `No such file or directory`) give one E520 and exit 1, an unknown step with `--step` gives one E706 and exit 1, and a spec folder that is not inside `--git-root` with `--paths` gives one E708 and exit 1 (with `--step` the report says `base: unavailable` and stderr gives the note `the spec folder <dir> is not inside the git root <root>, so it cannot be found in the repository`); plain `spec-check` on a missing spec folder prints every check with that E520 among the findings and exits 1. A spec file that cannot be read (no permission, or a folder named like a step file) gives one E520 from the `open-items` check, and the run goes on; with `--step` or `--paths` stderr also has the note `specdev spec-check: could not read <file>; the answer may be incomplete` (plain `spec-check` has the E520 only). `--step` with `--paths`, an empty `--base-ref`, and `--base-ref` or `--detail` without a gate are usage errors (exit 2). A path listed on `--paths` that lies outside the host root maps to no step, and the note for it gives the advice to pass `--git-root` only when `--git-root` was not given. A relative path after `--paths` is taken from the repository top: `--git-root`, else the top of the git working tree that holds the spec folder, else the folder that holds the spec folder. A step that a listed path maps to but that has no artifact in the spec folder is not gated, unlike with `--step`; when no step is left, stderr says `no step gated: no listed path maps to a step that has an artifact`. See `docs/developers/reference.md`, section "Step gate".

- `specdev verify bind <verifier-id> --command CMD [--command CMD ...] --guard REGEX [--proves ID ...] [--stage dev|ci|staging|prod] [--id ver-ID]` writes the verification record `spec/extras/verification/<id>.json` of a fixture, a job or a rule (never a spec file), and `specdev verify run [ver-ID ...] [--all | --milestone ms-ID] [--stage S] [--only-stage] [--no-record] [--installed TP=VERSION ...] [--timeout SEC]` runs the commands of bindings and writes one evidence record `evd-<name>-<stage>.json` (`<name>` being the binding id without its `ver-` prefix) for each, with the code-tree id of the run and the version that each declared source reads for the third parties the proved nodes rely on (those reached through the providing component's connections included). `verify run` exits 1 when a binding fails and warns W350 (a registered submodule with uncommitted content; an embedded repository that is not a registered submodule is not seen) and W351 (the run changed the code tree).
