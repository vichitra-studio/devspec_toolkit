## [1.1.0]

### Breaking Changes

- **`status_ref` field removed from the spec data model.** The optional
  `status_ref` canonical-reference field is removed from 21 schema properties
  across six schema files. All affected schemas use `additionalProperties: false`,
  so host spec files carrying `status_ref` will fail schema validation. Delete
  all `status_ref` objects from spec artifacts, remove orphaned `cn:*:status:*`
  entries from `canonical_refs_used[]`, and re-run `specdev spec-check`.

- **E590 cross-reference enforcement for step-11 mitigation IDs.** `specdev
  spec-check` now validates every mitigation ID (except `type: doc`) against the
  upstream step that defines it. Host specs with stale or invented mitigation IDs
  will fail `spec-check` with `E590 CROSS_STEP_ID_NOT_FOUND`. Switch invented
  `type: capability` IDs to `type: doc`, verify remaining IDs against their
  upstream steps, and re-run `spec-check`. Use the `/specdev-context` skill
  with an AI agent for bulk remediation.

### Added

**CLI**
- **`specdev update <spec_dir>`** — primary post-submodule-bump entry point.
  Re-stamps `spec/specdev_version` immediately when no structural schema changes
  are present; routes through the `specdev align` flow when migration is required,
  exiting 1 so CI catches un-migrated specs. Supports `--dry-run` and `--json`.

- **`specdev milestone-state`** — deterministic per-milestone phase-position
  computation for the Trinity loop. Reads the milestone plan file, probes
  `.specdev/findings/` under the host git root, and emits a JSON object with
  `milestone_id`, `groups[]`, `derived_phase_position`, and `blockers[]`.
  Replaces the LLM-evaluated mode in the `specdev-scope` agent with a
  unit-testable, run-to-run consistent computation.

**Validation**
- **W615 / E615 `INVARIANT_UNEXERCISED_BY_THREAT`** — new warning (promotable
  via `SPECDEV_WARNINGS_AS_ERRORS=1` or `SPECDEV_PROMOTE_CODES=W615`) fired when
  a step-06 invariant carries a `risk_category_ref` but no step-11 threat
  mitigation of `type: inv` references it.

- **`specdev matrix` now emits an `invariant_threat_coverage` map**
  (`inv_id → [threat_ids]`) derived from step-11 mitigations of `type: inv`.

**Schema**
- **`vc:canon:command-prefixes` schema** (`canon/command_prefixes.schema.json`)
  for the `command_prefixes.json` allowlist; registered in
  `tools/schema_registry.json`.

- **`specdev json insert --create-schema <uri>`** — bootstrap flag that seeds a
  missing target file with `{"$schema": "<uri>"}` and bootstraps the array-valued
  field before running standard differential validation. Enables first-use
  creation of `spec/canon/command_prefixes.json` without a separate
  file-creation step.

### Changed

- **Implicit differential schema validation on `specdev json patch` and `json
  insert`.** Every write is validated before it lands using the file's own
  `$schema` URI. A write is refused only when it *introduces* a new violation
  (before/after diff), so incremental one-patch-at-a-time repair workflows are
  not deadlocked. Writes are also refused when the file carries no `$schema` or
  when the write targets the `$schema` key itself. No `--no-validate` bypass is
  exposed.

- **`specdev-scope` agent `milestone_state` mode** now delegates to
  `specdev milestone-state` and passes its output through unchanged. The
  orchestration contract and `specdev-trinity` skill parsing are unaffected.

- **Trinity `verified`/`closed` transition** keyed on `implementation.status`
  string only. The previous dual-gate requiring both `status` string and
  `status_ref.id` is removed.

- **`prompt_11_redteam.md`** updated: net-new controls with no existing upstream
  artifact must use `type: doc` (exempt from cross-reference validation);
  `type: capability` is reserved for referencing an existing `cap-*` ID from
  Step 01.

- **E608 messages** now direct users to `specdev update` instead of
  `specdev align` directly.

### Fixed

- **Incorrect W→E promotions removed (`W597` and `W590`).** Two entries removed
  from `PROMOTABLE_PAIRS` where the warning and its same-numbered error describe
  structurally different defects: `W597` (vague intent text present) vs `E597`
  (upstream artifact has no intent entry at all); `W590` (upstream file absent)
  vs `E590` (referenced ID absent from a present file). Under
  `SPECDEV_WARNINGS_AS_ERRORS=1` or a matching `SPECDEV_PROMOTE_CODES`, these
  now stay warnings rather than mislabelling the defect.

- **`SPECDEV_PROMOTE_CODES` now warns on ignored codes.** When the variable
  lists a code that is not promotable or is unrecognised, `validate-all` and
  `spec-check` emit a one-time stderr warning instead of silently dropping it.

- **`spec-check` now honours W→E promotion in per-check results.** Previously,
  a check whose only violations were promotable W-codes still reported `WARN`.
  All per-check results now flow through a promote-then-classify path, making
  the per-check status, stderr breakdown, and JSON `findings` consistent with the
  active promotion contract.

- **`specdev json schema` now navigates step-specific and conditional-gated
  fields.** Previously, allOf branch merging overwrote a node's own `properties`,
  causing `specdev json schema` to be unable to navigate step-specific keys such
  as `.plan`, `.execution`, and `.review` on step-16 plan files. The fix resolves
  properties own-first and unions `oneOf`/`anyOf`/`if-then-else` branches for
  discovery.

- **`specdev validate` / `spec-check` now fail closed on all registry I/O
  errors.** Previously only `FileNotFoundError` was caught; `PermissionError` and
  other `OSError`s escaped uncaught. All I/O errors now route to
  `E520 schema_not_found`.

- **`specdev validate` step-11 validator now handles malformed `threats[]` and
  `target_ids[]` entries.** Non-dict entries previously raised an unhandled
  `AttributeError`; they now emit a structured `E520` instead.

- **`E541 UNBOUND_CANONICAL_TERM` no longer fires on structurally-unbindable
  fields.** Follow-up to the `status_ref` removal in this release: objects whose
  schema declares `additionalProperties: false` with no `*_ref`/`*_refs` slot
  cannot bind a sibling reference, so requiring one to satisfy E541 was a schema
  contradiction. `hallucination_lint` now loads each file's resolved JSON Schema
  and suppresses E541 on free-text fields of structurally-unbindable objects,
  while ref-capable objects (e.g. `14_roadmap` milestones with
  `fr_refs`/`capability_refs`) still fire. Affected surfaces:
  `plan.ambiguities[].description`, `plan.docs_impact.rationale`,
  `milestones[].name`, and `execution.final_status.test_results[].name`.
  Additionally, the runtime ref-presence suppressor is now **term-specific**:
  a sibling `*_ref`/`*_refs` suppresses E541 only for the term whose canonical
  ID it actually binds, rather than silencing every free-text field on the
  object. An unrelated reference no longer masks a genuinely unbound term.

- **`specdev align status` no longer recommends migration on a version
  downgrade.** When a project is on a *newer* toolkit version than the one it
  references (source > target), `format_status_report` previously printed
  "⚠️ Migration recommended" because `calculate_version_delta` returns `None`
  for a downgrade and the formatter conflated that with "update required". It
  now emits an informational "project is ahead of toolkit" line and recommends
  no migration.

- **`specdev align` no longer mis-reports step 16.** Step 16 ships two schemas
  but only one root spec file: the Trinity Anchor at `spec/16_impl_context.json`
  is validated against `vc:16-anchor`, while per-milestone plans under
  `spec/impl_context/` use `vc:16-impl-context`. The schema differ previously
  flagged the root anchor as `NEEDS UPDATE` (wrong `$schema`) and reported a
  spurious `MISSING` `16_anchor.json`. The differ now maps the root step-16 file
  to the anchor schema per the prompt contract; a correct host layout reports
  step 16 fully OK, while a genuinely-wrong layout still flags.

### Removed

- **`--against-schema-field` flag** removed from `specdev json patch` and
  `specdev json insert`. The flag was broken (wrong schema selected for
  multi-schema steps; top-level-only resolution could not validate nested writes)
  and is replaced by the new always-on implicit validation. The `specdev-context`
  skill no longer mandates this flag.

- **`status_ref` removed from 21 schema properties** across
  `schema/04_fr_list.schema.json`, `schema/06_invariants.schema.json`,
  `schema/09_impl_plan.schema.json`, `schema/14_roadmap.schema.json`,
  `schema/16_impl_context.schema.json`, and `schema/core/collections.schema.json`.

- **Canon `status` kind retired.** `canon/kinds/status.json` (7 entries), 7
  status aliases, and 14 `kind: "status"` entries removed from
  `canon/manifest.json`. Schema string enums are now the single source of truth
  for status vocabulary.
