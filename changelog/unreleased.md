### Breaking

- Steps 00 to 05 move to the spec-graph shape; existing host specs do not validate until migrated (the migration passes land later in this release). Step 00: `in_scope` / `out_of_scope` merge into `scope_items` (each with `scope` `in` | `later` | `out`, `scope_reason` for `later` / `out`, `scope_id`), and the 1.1.1 floor of three entries in each of the two lists becomes one entry in `scope_items`; assumptions, risks and stakeholder needs become objects with ids (they were strings), stakeholders gain `stakeholder_id`, new `constraints` list, `links` removed, `derives_from` added to scope items, assumptions, risks, needs, segments, metrics and constraints. Step 01: capabilities lose `goal_id`, `success_metric_refs` and `trace` and gain `derives_from` and `scope_reason`; the `scope` value `future` becomes `later`. Step 02: components and connections lose `trace`; component `type: external` and the tag `external-dependency` removed (model the service as a `third_parties` entry); connections lose `from`, `to`, `schema_ref` and `interface_ref` and gain `connection_id`, `derives_from` (source) and `connects_to`; new `third_parties` (`tech_stack` removed). Step 02a: artifact-level `trace` removed; `ci_gates` and `secrets` become objects (`gate_id`, `secret_id`); each environment gains `scope`, `derives_from` and a `config` object that holds the host keys. Step 03: terms gain `aliases`, `lifecycle`, `replaces`. Step 04: FRs lose `trace` and gain `derives_from` (capabilities) and `depends_on` (FRs); acceptance criteria gain `scope`. Step 05: APIs lose `trace` and `example_refs` and gain `derives_from` (FRs), `provided_by`, `relies_on` and `depends_on`; each error gains required `error_id`, `scope` and `derives_from`. `scope` (`in` | `later` | `out`) becomes required on every functional requirement, API, API error, acceptance criterion, charter risk, environment, CI gate and secret; none of them had it in 1.1.1 (capabilities already required it). `scope_reason` is required wherever `scope` is `later` or `out`, capabilities included (1.1.1 had no such rule). `derives_from` with at least one id becomes required on every node of steps 00 to 05 except stakeholders, glossary terms and acceptance criteria. A stakeholder needs at least one need. Every node accepts `aliases`, `lifecycle` and `replaces`; every node except an assumption and a glossary term also accepts `assumes`.  `specdev align status` / `diff` / `plan` report nothing for a 1.1.1 spec of steps 00 to 05 against the new schemas, top-level renames such as `in_scope` to `scope_items` included, because the differ reads only a schema's own top-level `required`, `properties` and `additionalProperties`, and these step schemas keep their properties under `allOf`.
- Link-existence checks are removed from the step validators of 01 (capability to component; `validate_step_01` now returns no errors), 02 (connection endpoints) and 05 (API to requirement, with its W590 for a missing step 04 file). They are replaced by the `graph` check of `spec-check` (E700 to E703); a single-file `specdev validate` of those files does not report a link to an id no node has. The step 04 check that a requirement carries a non-empty `trace` and the step 02 check for a missing `tech_stack` go with those fields. The step 02 capability-coverage check (E590) stays; it now reads component `derives_from` and exempts capabilities whose `scope` is `later` or `out`. Other content checks stay, for example the duplicate method and route check of step 05 (E520).
- A check that reads fields of the 1.1.1 shape (`trace`, `goal_id`, `success_metric_refs`) runs only when the files it reads carry those fields. A spec whose steps 00 to 05 have the new shape gets none of E560, W564 / E535 and W568, and no FR-to-API coverage finding from the matrix (W592, or E592 when `coverage_thresholds.mode` is `error`), whatever shape its later steps have, until graph coverage later in this release. A 1.1.1 spec whose step-05 APIs carry no `trace` at all gets no W564 and no W592 / E592; such a file is invalid under the 1.1.1 schema. For a spec whose steps 00 to 05 have the new shape, `completeness-check` reports FR-to-API coverage and capability-to-FR coverage as complete (ratio 1.0), because the checks behind those two numbers do not run on it, until graph coverage later in this release (once steps 06 to 16 have the new shape as well, FR-to-fixture and FR-to-milestone coverage join them: see `completeness-check` under Changed). For the same spec `specdev matrix` omits `fr_with_api` and the `apis` of each FR row and names them in a top-level `not_computed` list, because its FR-to-API reader does not run on it; no W592 / E592 follows from that. The step-11 W583 check reads API `derives_from`: a 1.1.1 step-05 API linked only to parked requirements through `trace` is no longer exempt from W583.
- Steps 06 to 16 move to the spec-graph shape, with the core schemas they share; existing host specs do not validate until migrated. No migration path exists yet for a 1.1.1 spec to this shape: the `align` migration passes land in a later 1.2.0 change, and `specdev align status` / `diff` / `plan` read only a schema's own top-level `required`, `properties` and `additionalProperties`, while the step schemas keep most or all of their properties under `allOf`, so they miss the changes below, top-level ones included (`align diff` reports a 1.1.1 file of step 07, 08, 11 or 14 as `OK`). `specdev update` decides with the same comparison, so it re-stamps `spec/specdev_version` on such a spec as if nothing had changed.
- Core and every step schema: `spec_refs_ingested` and `seed_refs_ingested` are removed from steps 00 to 16 (13a, `16_anchor` and `16_impl_context` included) and from `core/step_base`, with the definitions `specRefIngested*` and `seedRef*`. Steps 00 to 15 except 13a gain an optional top-level `ambiguities` list of open items: each item has `id`, `description` and `about` (ids it concerns), and optional `missing_kind`, `decision` and `proposed_assumption`; it has no other field. `plan.ambiguities` in `16_anchor` and `16_impl_context`, and `execution.emergent_ambiguities` in `16_impl_context`, use the same open item: `severity`, `status`, `impact` and `resolved` are removed (and `source` and `mitigation` from `plan.ambiguities` of `16_impl_context`), and `about` is required. The core definitions `crossCycleAmbiguityItem` and `ambiguityStatus` are removed. `testingMode` and step 08 `fixtures[].mode` gain the value `manual`. The core definitions `dependencyList`, `techStack`, `techStackItem`, `techStackList`, `dependencyItem`, `dependencyObjectList`, `link`, `httpMethodFull`, `traceRef` and `traceId` are removed with their last use.
- Steps 02, 04 and 05 (finishing the step 00 to 05 change above): `tech_stack` is removed from step 02 (use `third_parties[]`); the `priority` value `wont-have` is removed from step 04 functional requirements (use `scope: later` or `scope: out`); the top-level `out_of_scope` list is removed from step 05 (mark the requirement `scope: out` with a `scope_reason`).
- Steps 06 and 07: `rules[].trace` (step 06) and `nfrs[].trace` (step 07) are replaced by `constrains`, an optional list of ids of functional requirements, APIs, components or connections. Step 06 `rules[].scope`, an object `{components, apis}` in 1.1.1, becomes the string `in` | `later` | `out` (default `in`; `later` and `out` need `scope_reason`). Step 07 gains optional `relies_on` (third parties), `derives_from` (metrics) and `scope` / `scope_reason`. Both steps gain optional `assumes`, `lifecycle`, `aliases` and `replaces` on every node. The node kind of step 06 is `invariant`.
- Step 08: `fixtures[].targets` is replaced by `verifies` (ids of acceptance criteria, APIs, invariants or NFRs; not FRs), and the top-level `out_of_scope` list is removed. A fixture needs `verifies` or `removes`. New optional `manual_reason` (a string of at least 10 characters), required when `mode` is `manual`. Fixtures gain `lifecycle`, `aliases` and `replaces`.
- Step 09: the top-level `tech_stack`, `tech_stack_ref`, `trace`, `dependencies` and `dependency_ref` are removed, and `milestones` is the step's own required top-level field (the step-base fields `id`, `owner`, `created_at` and `canonical_refs_used` stay required). Each milestone loses `status`, `deliverables` and `depends_on` and requires `schedules` (at least one id of a functional requirement, acceptance criterion, API, invariant, NFR, component, environment or risk); it gains `lifecycle`, `aliases` and `replaces`. The node kind is `design-milestone`.
- Step 10: `pr_rules`, `spec_first_policy`, `review_policy`, `reviewers`, `trace` and `links` are removed. `rules` (at least one) is required beside `commit_message_rules`. Each rule (node kind `rule`) needs `rule_id`, `text` and `derives_from` (at least one id of a constraint, risk, scope item, gate, environment or stakeholder), and may carry `enforcer` (only `review`), `cli_command`, `assumes`, `scope`, `scope_reason`, `lifecycle`, `aliases` and `replaces`; a rule with `enforcer` must not carry `cli_command`. `versioning`, `policy_ref` and `command_ref` stay.
- Step 11: the artifact-level `trace` is removed. A threat's `target_ids` becomes `threatens` (required, at least one id of an API, component, connection or third party) and `mitigations` becomes `mitigated_by` (optional ids of functional requirements, criteria, APIs, API errors, invariants, NFRs, rules, gates, secrets, environments, constraints or fixtures); a threat gains optional `derives_from` (risks). An edge case now requires `threatens` (APIs, components or FRs) and `mitigated_by` (at least one id). Threats and edge cases gain `scope`, `scope_reason`, `assumes`, `lifecycle`, `aliases` and `replaces`. The node kinds are `threat` and `edge-case`.
- Step 12: `trace` is removed. `jobs[].requires` is renamed `jobs[].depends_on` (ids of jobs of the same file), and `jobs[].steps[].id` is removed (a step needs `name` and `command`). Jobs gain optional `realises` (environments, gates, secrets or rules), `verifies` (NFRs), `lifecycle`, `aliases` and `replaces`. The node kind is `job`.
- Step 14: the top-level `tech_stack`, `tech_stack_ref`, `dependencies`, `dependency_ref` and `trace` are removed. A milestone loses `status`, `milestone_status_reason`, `source_milestones`, `fr_refs`, `capability_refs` and `deliverables`, and requires `milestone_id`, `name`, `target_date`, `user_story` and `tasks` (node kind `roadmap-milestone`). A task loses `status`, `status_reason`, `assumptions`, `exit_conditions`, `fr_refs` and `invariant_refs`; its `depends_on` items are kebab-case task ids; it gains `disposition` (`value`: `deferred` or `wont_do`, and `reason`, both required) to set a task aside (node kind `task`). An acceptance criterion's `fixture_ref` is renamed `verified_by` (ids of fixtures, jobs or rules), and the criterion needs `refines` (at least one id of an upstream node) or `removes` (at least one id) (node kind `task-criterion`). Milestones, tasks and criteria gain `lifecycle`, `aliases` and `replaces`.
- Step 15: `trace` and `links` are removed. Each `interface_map[]` row loses `interface_ref` and `method` and requires `row_id` (a kebab-case id), `realises` (at least one API id) and `path`; an API may be realised by several rows. Rows gain `lifecycle`, `aliases` and `replaces`. The node kind is `scaffold-row`. `project_skeleton`, `validators`, `command_ref` and `build_status` stay.
- Step 16 anchor (`16_anchor`): each `plan.milestone_index[]` row loses `milestone_id`, `context_path` and `fr_refs`. A row requires `anchor_id`, `about` (the id of one roadmap milestone), `checklist_id_prefix` and `summary`; `status` stays and is optional, and an absent `status` reads as `pending`. `deferral_reason` is required when `status` is `deferred`; `close` (`signed_off_by`, and `source` when `signed_off_by` is `legacy-migration`) is required when `status` is `done`. The node kind is `anchor-row`.
- Step 16 plan (`16_impl_context`): the file requires a file-level `milestone` (the roadmap milestone id the plan is about), and the anchor validator finds the plan of an anchor row through it (`milestone-state` still finds a plan by its file name). `plan.status`, `plan.deferred_reason` and `plan.coverage_status` are removed. A plan item (`plan.spec_alignment.checklist[]`, node kind `plan-item`) loses `spec_ref`, `milestone_ref`, `nfr_refs`, `fixture_ref`, `checklist_status`, `deferred_reason`, `wont_do_reason`, `linked_test_expectation` and `implementation.status`; it requires `id`, `realises` (at least one task-criterion id), `description` and `implementation`, and gains `lifecycle`, `aliases` and `replaces`. Also removed: `plan.spec_alignment.requirements_summary[].spec_refs`, `plan.security.new_fixtures`, `plan.security.spec_mutations`, `execution.critical_evidence`, `execution.execution_results[].evidence_binding`, `review.fixture_status.test_results` and `extensions.review_state`; `review.findings[].spec_ref` loses `line_range` and `commit_hash`; `review.fixture_status.implemented_interfaces[]` items are plain kebab-case ids. ### Added

- `schema/core/graph.schema.json` (`vc:core:graph`): the `x-node` / `x-link` annotation language for declaring graph nodes and links in step schemas. See `docs/developers/schema-annotations.md`. The seed manifest (`schema/seed_manifest.schema.json`) and the step schemas 00, 01, 02, 02a, 03, 04 and 05 are annotated; the schemas of steps 06 to 12, 14, 15 and 16 are annotated too; the schemas of steps 13 and 13a carry no annotation of their own (step 13 gets the shared `ambiguity-item` node through the core `ambiguityList`).
- Annotation reader and lint with `ANNOT-NN` toolkit-author codes, and a step-order derivation (`ANNOT-20` cycle, `ANNOT-21` same-step link). `registry-generate` folds annotated nodes into `entry_key_registry.json`; without annotations the entries are unchanged and `_format_version` is `1.1.0`.
- `tools/cli_commands.json` (generated; `schema/cli_commands.schema.json`) and the `registry-generate` flags `--cli-commands-out` and `--step-order-out`. Toolkit-internal: no host action.
- New commands for reading the spec as a graph (`graph/commands.py`); each takes `--repo-root`, `--spec-root` (default `./spec`), `--git-root` (default: the folder that holds `--spec-root`) and `--json`. `specdev node <id> [<id> ...] [--full]` (also `specdev node show <id>`, which reads an id that is itself a subcommand name) shows a node: file and jq path, content, links out and the number of links in. `specdev node candidates (--kind KIND | --for ID) --field FIELD [--query TEXT] [--limit N]` lists the nodes a link field may point at. `specdev node status <id> active|deprecated|not_applicable` writes the node's `lifecycle` into its spec file (`active` removes the key from a node that has another value) and prints `<id>: <old> -> <new> (<file>)`; a node that already has the value is not written, an explicit `"lifecycle": "active"` in its file included, and the line reads `<id>: already <value>, nothing written (<file>)`. `specdev trace <id> [--up] [--down] [--depth N] [--kinds K,K] [--verbs V,V] [--no-containment]` lists what the node rests on and what rests on it. `specdev trace <id> --recipe 16a|16b|16c [--expand] [--since REF]` prints the context pack of a role. `specdev diff <refA> <refB>` compares the graph at two git refs (the working tree is not read) and prints a suggested version bump. A command that cannot answer prints one finding on stderr (with `--json`, the `status` / `errors` envelope on stdout) and exits 1, for example: E705 for a lifecycle change that is refused (a seed node, an unknown id, a lifecycle value that is not one of the three, a write the JSON tools refuse), E706 for an unknown id, kind, link field or recipe role, E707 for a recipe start node of the wrong kind, E708 for a ref that does not resolve or a spec folder that cannot be read at it, E709 for a ref whose tree has no graph node (a tree from before 1.2.0 that has ids the registry reads is compared as it is, and the result is not meaningful), E520 for a spec folder that is missing. When a spec file cannot be read, `node`, `node candidates`, `node status` and `trace` print one more line on stderr that names the file and says the answer may be incomplete, and an unknown id then says the node may be in one of those files. The commands are listed in `tools/cli_commands.json`.
- `specdev spec-check` runs a new check, `graph` (before `registry-check`), over the whole spec: E700 (a link names an id no node has; when a spec file that could hold the target could not be read, the message says so), E701 (a node of a kind the field does not accept), E702 (a node of a later step), E703 (a cycle within one step, one finding per cycle) and E704 (an id defined more than once). In `spec-check --json` these findings carry `owner` (for example `step:12`) and `node_id`. The `graph` check reports W720 (a link to a deprecated node) and E761 as well (see the trace lock below). `validate-all` does not run the check; it reports the trace-lock findings listed below.
- The trace lock `spec/extras/trace.lock.json` (`$schema` `vc:extras:trace-lock`, `schema/extras/trace_lock.schema.json`) holds one entry for each link of the spec: the holder, the field, the target, and the content hash and chain stamp (`sha256:` and 64 hex digits) the target had when the holder accepted the link. A link whose target now has another chain stamp is a suspect link (E763); the cause is `content_changed` (the target was edited) or `upstream_changed` (a node above it was). Links held by the nodes of a closed milestone (an anchor row with status `done`) are not suspect and cannot be re-attested (E765). The worked example carries a lock of 64 entries. A host that has no lock file gets E761 (a link with no entry) once per link from `spec-check` and `validate-all`; `specdev attest <node-id> --yes` creates the entries of a node. `spec-check` runs three new checks: `trace-lock` (E760 for a lock that cannot be read, E762 for an entry whose link is gone, E763, E882 for a `baseline` marker that no `attest` has cleared), `computed-fields` (E768 for a stored computed field such as `content_hash`) and `records` (E774 for an invalid record file); the `graph` check also reports E761, W720 (a new link to a deprecated node), E771 (an alias that collides), E772 (a `replaces` link to a node still in the spec) and E778 (a live node that links by an old id). `validate-all` reports E760 to E763, E778, E882 and W720 too. The error-code catalogue has an entry for each, with a message copied from a run. Until a later 1.2.0 change, the skills and agents under `.claude/` write links with the path form of `specdev json` (`json patch <file> <path> <value>`), which writes no lock entry, so a spec with links reports E761 after such a write.
- `specdev stale [--step NN] [--diff]` lists the suspect links by owning step in waterfall order, nodes upward first, with the cause and the nodes the change started from (`roots`); `--diff` adds the diff of each root's contract text against the text the holders accepted, recovered from git (one diff for each accepted version when the holders below one root accepted different ones). It exits 0 when it lists links, and an unknown step is E706; a spec file that cannot be read is a warning on stderr and a lock that cannot be read is E760, exit 1. `specdev attest <node-id> [--field F] [--target T]`, `attest --step NN` and `attest --prune` write the current hashes into the lock for the suspect links of a node, of a step (upward first) or remove the entries of links that no longer exist; **without `--yes` the first two print what they would write and write nothing**, `--dry-run` never writes, with or without `--yes`, and `--prune` writes at once; `--target` takes an id or an alias. Refused with exit 1: E520 (`--yes` or `--prune`, each with or without `--dry-run`, while a spec file cannot be read, so the links it holds are not in the graph, and `--yes` also while a seed document is not found under the host root (`--git-root`, or the folder that holds `--spec-root`), because the hash of a link to it would be that of a missing file; nothing is written; a preview, with no `--yes`, still prints, with a warning on stderr that the answer may be incomplete, or a note on stderr that a seed document is not found), E764 (a node the holder links to is itself suspect: attest that one first), E765 (a node of a closed milestone), E706 (an unknown id or step), E704 (an id defined twice). `specdev coverage [--by fr]` prints how many FRs have an API or a fixture and how many capabilities have an FR, the criteria that have a current refinement and the exempt nodes (`not_applicable`, scope `later` or `out`); it prints information and exits 0 when it shows the counts and gaps, because no rule requires those links; a spec file that cannot be read is a warning on stderr and a lock that cannot be read is E760, exit 1. The role-rule findings of `coverage` and the coverage gaps of `stale` stay empty until a later 1.2.0 change registers the rules.
- `specdev lock merge BASE OURS THEIRS PATH` is a git merge driver for the lock: it merges the three versions entry by entry and writes the result over OURS (E760 for an input that is not a valid lock, E520 for a file that cannot be read); when both sides changed one entry in different ways it keeps the entry the common ancestor had, or, when it had none, the entry with the smaller chain stamp (string order), and the link is suspect again when its target changed after the kept entry. `specdev lock install-driver --driver-command CMD` adds the line `<path of the lock relative to the git top level> merge=specdev-trace-lock` (`sub/spec/extras/trace.lock.json merge=specdev-trace-lock` for a spec folder `sub/spec`) to the file `git rev-parse --git-path info/attributes` names and sets `merge.specdev-trace-lock.driver` to `CMD %O %A %B %P` in the clone at the git root (`--git-root`, or the folder that holds `--spec-root`); running it again changes nothing. Until a later 1.2.0 change no setup script installs the driver into a host: run `lock install-driver` once in each clone, otherwise git merges the lock as text, and a conflict leaves conflict markers in it, which `specdev` reports as E760 with the repair.
- `specdev json patch|insert|delete --id <node-id>` and `specdev json insert --step NN` write by node id: the field path is relative to the node, ids the new item leaves out are minted, the lock entries of the links the edit adds are written and those of the links it removes are dropped, and the command lists the links the edit leaves suspect (`newly suspect: ...`; `would become suspect: ...` with `--dry-run`) and, for a delete, the links that now point at a node that is gone (`now broken`). With `--dry-run` the report says `lock entry to write` and `lock entry to remove`, and nothing is written. Refused with exit 1: E767 (a seed, the node's own id, an edit that adds a schema violation or leaves a link that does not resolve or an alias collision, an `insert --id` into a field the node does not have and its schema does not declare as an array, or into a field that holds a string, an object, a number or a boolean, a path that is not a node collection of the step, the path of a collection that is a map keyed by id), E768 (the payload stores a computed field), E706 (an unknown id or step), E769 (another specdev write is running; the write lock is on the spec folder), E520 (a spec file cannot be read, so the links it holds are not in the graph, or a seed document is not found under the host root, so the hash of a link to it would be that of a missing file; also for a dry run). `json insert --id` creates the first item of an array field that the node lacks and its schema declares. These forms take `--repo-root`, `--spec-root`, `--git-root` and `--json` (CLAUDE.md says the `json` subcommands take `--repo-root` only: that holds for the path forms); `json delete`, `json keys` and `json structure` now accept `--repo-root` too.
- `specdev step create NN --from DRAFT [--dry-run]` writes the file of step NN from a draft that holds the whole artifact (ids of sub-items may be left out), checks it against the step's schema, requires every link to resolve and writes the lock entries of its links; E767 when the step already has its file, for steps 13a and 16 to 16c, for a draft that cannot be read, for a draft whose `$schema` is not the step's and for a link that does not resolve; E520 when a spec file cannot be read or a seed document is not found under the host root (also for a dry run). `specdev step ready NN` prints `step NN: ready` and exits 0 when the steps NN links to have a spec file and no pending replay, and otherwise reports E773 with the blockers and exits 1, naming the step to write first (a step with no file) or to replay first; E520, exit 1, when a spec file cannot be read; the file of NN itself is not required. Until a later 1.2.0 change retires step 13a, `tools/step_order.json` still lists it as an input of 14 and 16a, so `step ready 14` reports E773 on a spec with no 13a file.
- `specdev node rename OLD NEW [--dry-run]` changes a node's id in one change: the old id goes into the node's `aliases`, the links that live nodes write to it are rewritten, and the lock entries of those links and of the node's own links are re-keyed with their hashes unchanged, so a rename makes no link suspect (link ids are hashed under the target's first name, the first entry of its `aliases`). Links held by closed milestones and by records keep the old id and resolve through the alias. `specdev node rename --label TERM_ID "NEW LABEL"` changes a glossary term's label and rewrites every use of the old label in the text of nodes of steps 04 to 15, except in nodes of a closed milestone, which it lists as not rewritten; the nodes whose text changes, and the nodes that link to them, become suspect. `specdev diff` prints `<new id>: renamed from <old id>` for a rename and suggests the bump `patch`. Before it writes, it checks the schema of the files it edits and the findings of the graph; it does not run the step validators, so a new id that breaks the id convention of a step is written and `spec-check` reports it (E530). A plan item can be renamed. Refused: E770 (a seed, a record, an environment, an id that a node or an alias has, the same id, a rename that adds a schema violation or a finding, a label of something that is not a glossary term), E706 (an unknown id), E520 (a spec file cannot be read, so the links it holds are not in the graph; also for a dry run).
- Verification and evidence records: the kinds `verification-record` and `evidence-record`, the schemas `vc:extras:verification-record` and `vc:extras:evidence-record`, and the files `spec/extras/verification/ver-<id>.json` and `evd-<id>.json`, each `{"$schema": ..., "records": [one record]}` with the record id as the file name. The worked example has `ver-password-reset-expired-token.json`. `spec-check` reports E774 for an invalid record file (check `records`); a `verifies` or `about` id that no node has is E700 from the `graph` check. `validate-all` does not read record files.
- New error codes E760 to E765, E767 to E774, E778 and E882 (E766 does not exist), in the catalogue `docs/developers/error-codes.md` and registered in `tools/specdev_tools/core/errors.py`. `tools/cli_commands.json` lists the new commands (46 top-level commands).
- `specdev spec-check` gates one step: `--step N` (repeat it for several steps; a step given twice is gated once) blocks on the errors that step N owns and on errors of earlier steps that are new since the base; `--paths FILE...` (every word up to the next option; zero or more files; write `spec_dir` before it) gates the steps of the files you list; `--base-ref REF` names the base branch (default: `SPECDEV_REPLAY_BASE_REF`, `origin/HEAD`, `origin/main`, `origin/master`, `main`, `master`); `--detail {summary,all}` lists upstream debt, pending and gate-owned findings in full. The report goes to stdout and notes to stderr, and the exit code is 1 only when the result is BLOCKED, with `--json` too. A new error is told from an old one by the tuple (code, owner, node id, link target, file, jq path with the array indexes removed, subcode, path), never by its message, and by count: for each tuple, a finding is new only when the working tree has more findings with it than the base had. A reworded message, or an item inserted before an old error, is not new. One limit: an error fixed and another of the same tuple added on the same branch reads as no change at the step gate; plain `spec-check` still lists both, and the merge check, which no command runs yet, reports every error. With several steps each bucket of the `--json` report is the union over the steps. When no base can be used the report says `base: unavailable`, every upstream error counts as new, and stderr gives the reason. A spec folder that does not exist, and a toolkit with no readable `tools/error_ownership.json`, give one E520 and exit 1. A spec file that cannot be read gives one E520 from the `open-items` check and the run goes on. `--step` with `--paths`, an empty `--base-ref`, `--include-forward-replay` with either, and `--base-ref` or `--detail` without a gate are usage errors (exit 2). A relative path after `--paths` is taken from the repository top: `--git-root`, else the top of the git working tree that holds the spec folder, else the folder that holds the spec folder. See `docs/developers/reference.md`, section "Step gate".
