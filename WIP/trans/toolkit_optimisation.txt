1. OVERVIEW
═══════════════════════════════════════════════════════════════════════════

This document plans the optimization of the devspec_toolkit's AI-assisted
spec authoring workflow. The core problem: when an AI agent authors a spec
step, it reads entire upstream spec files (1500+ lines each) when it only
needs a few fields. Across a 22-step pipeline: ~59k tokens ingested, ~19k
actually needed. 40k tokens wasted per pipeline run.

The solution is a three-layer architecture:

  Layer 3: Skills + Hooks (Claude Code automation)        ← orchestrates
  Layer 2: specdev context (toolkit-aware slicing)        ← scopes + extracts
  Layer 1: json_utils (generic jq wrapper)                ← targeted CRUD
  Layer 0: specdev validate / lint / matrix (existing)    ← validation

json_utils is built (696 lines, tools/core/json_utils.py). The context
package (Layer 2) is the next deliverable. Skills/hooks (Layer 3) follow.

Core principle: Tools prepare data and validate output. Claude Code
reasons and generates. No tool ever calls an LLM.

2. DECISION HISTORY
═══════════════════════════════════════════════════════════════════════════

Key reasoning chains from the initial analysis sessions (Feb 28 – Mar 1,
2026), distilled from conversation transcripts.

2a. Why token optimization matters

  The extraction_intent field in step_order.json (since removed in G4)
  told each step which fields to extract from upstream specs — but
  nothing enforced it. The AI read entire 1500-line specs when it needed
  3 fields. Quantified waste:

    Step 04 (FRs): 5,000 tokens ingested, 1,200 used (76% waste)
    Step 09 (Impl Plan): 10,000 ingested, 3,000 used (70% waste)
    Step 16a (Planner): 15,000 ingested, 4,000 used (73% waste)

  Root cause: no tooling existed to slice specs before they reached the
  AI. json_utils blocks full-file reads (jq filter "." rejected) but
  nothing connects the pipeline graph to the slicing logic.

2b. Why scope-based extraction, not full-file reads

  Static field projection (extract .goals, .constraints from charter)
  works for early steps (00-05) where the full upstream spec is relevant.
  But from Step 06 onward, what you need is determined by the trace
  graph. Step 16a working on milestone-02 doesn't need all 50 FRs — it
  needs fr-payment-create and fr-payment-refund (the ones tied to that
  milestone's tasks).

  The extraction is graph traversal, not field projection:
    milestone ID → task IDs → FR IDs → specific FR objects → their
    traced APIs → those API contracts

  The trace_matrix (generated by specdev matrix) already builds this
  graph. It just wasn't used for context slicing.

2c. Why the review phase was added

  The original flow was: read prompt → ingest seeds → clarify/emit →
  validate → report. This validated schema conformance but never checked:

  - Did the artifact capture everything from the seeds?
  - Are all upstream spec requirements distilled into this step?
  - Were any seed requirements silently dropped?
  - Is there scope creep (output elements with no upstream justification)?
  - Was meaning preserved (not just ID linked)?

  The fix: a two-pass review gate between emit and validate. Pass 1 is
  structural (automated ID coverage, reverse trace, acceptance criteria
  matching). Pass 2 is semantic (only for flagged items — Claude judges
  surgical source/target text pairs). This keeps the review under ~3k
  additional tokens instead of re-reading all upstream specs at full depth.

2d. Why graph-driven slicing for late steps

  Early steps (00-05): full upstream specs are small and mostly relevant.
  Field projection suffices (~60-75% token reduction).

  Mid steps (06-12): some arrays are relevant, others aren't. Scope
  resolution walks capability → FRs → APIs.

  Late steps (13-16c): the entry point is a milestone or task ID. The
  scope resolver walks: milestone → tasks → FR IDs → specific FR objects
  → their traced APIs → those API contracts → relevant fixtures/NFRs.

  Result: Step 16a scoped to milestone-02 needs ~3,730 tokens instead of
  ~25,000+ (85% savings).

2e. Why toolkit-aware wrapper, not json_utils extension

  json_utils is a generic jq wrapper — it doesn't know about steps,
  traces, scopes, or the spec pipeline. The user explicitly said:
  "json_utils is supposed to be a very low level general purpose util.
  I would rather build a wrapper around it which is toolkit specific."

  This led to the context package design: json_utils stays generic,
  specdev_tools/context/ is the toolkit-aware brain.

2f. Why SDK-free architecture

  Claude Code IS the LLM in the loop. The toolkit never calls an LLM
  directly. Tools output structured data (JSON, tables, prompts). Claude
  Code (already running) does the reasoning. Tools validate Claude Code's
  output. No API keys, no SDK dependency, no billing beyond the Claude
  Code session. The toolkit remains pure Python CLI tools.

  Only 2 interactions need Claude: seed indexing (one-time extraction from
  prose) and reviewer semantic pair judgment (targeted, ~50 tokens per
  flagged pair). Everything else is deterministic Python.

2g. Why seed propagation was trimmed to Steps 00-04

  All 22 pipeline steps were told to read raw seed documents, even though
  Steps 00-04 already distill all seed content into structured JSON specs.
  Steps 05+ work entirely from upstream specs. The fix:

  - seed_manifest.json step_requirements trimmed to 00-04 only
  - Prompts for 05-16c: removed seed file references
  - Output contract examples: seed_refs → [] for 05-16c
  - Self-Audit Gate: explicitly states seed_refs is [] for 05-16c
  - Schema: seedRefArray minItems 0 (allows empty)

  seed_indexer.py and seed_reviewer.py (originally planned for the context
  package) were dropped — redundant with the existing pipeline.

3. ARCHITECTURE
═══════════════════════════════════════════════════════════════════════════

3a. Three-layer stack

  ┌──────────────────────────────────────────────────────────┐
  │  Layer 3: Skills + Hooks (automation)                    │
  │    Skills = slash commands that prepare context           │
  │    Hooks  = auto-triggers (post-edit → validate)         │
  │    CLAUDE.md = teaches Claude the pipeline graph          │
  │      ↓ consumes                                          │
  │  Layer 2: Context Package (data/scoping)                 │
  │    structure, scope_resolver, extractor, canon_extractor, │
  │    reviewer, freshness                                    │
  │      ↓ uses                                              │
  │  Layer 1: Infrastructure (already built)                  │
  │    json_utils, step_order.json, schema_registry.json,    │
  │    SchemaRegistry, trace_matrix                           │
  └──────────────────────────────────────────────────────────┘

3b. Reference structures

  The toolkit has 2 directed graphs and 2 supporting indexes:

  Trace graph — fr→api→nfr→fixture via trace[].id arrays in spec
  artifacts. Traversed by trace_matrix. Primary graph for scope
  resolution.

  Step dependency graph — downstream_consumers DAG in step_order.json.
  Enforced by dependency-order-lint and dag-lint. Used for input
  selection ("which specs feed this step?").

  Canon vocabulary index — canonical_refs_used[].id → cn: entries in
  canon/manifest.json. Flat per-artifact annotation, NOT a directed
  graph. Useful as a review signal for vocabulary drift between steps.
  Not useful for scope resolution.

  Schema composition tree — $ref chains across schema files
  (vc:core:step-base → vc:core:atoms → etc.). Internal to extractor
  implementation and schema validation.

3c. Spec step flow

  ┌─────────────────────────────────────────────────────────┐
  │  /specdev-step <NN> [--scope <entry-id>]                 │
  ├─────────────────────────────────────────────────────────┤
  │  1. ORIENT       specdev context structure --step NN     │
  │     → shape of all inputs + canon kinds needed  ~200 tok │
  │  2. SCOPE        specdev context scope --entry <id>      │
  │     → resolved ID set (FRs, APIs, NFRs needed)  ~150 tok │
  │  3. EXTRACT      specdev context extract --step NN       │
  │     → only the objects in scope               ~700 tok   │
  │  4. CANON        specdev context canon --step NN         │
  │     → relevant canon vocabulary entries      ~200-400 tok │
  │  5. SEEDS        Read seed docs (small prose)   ~800 tok │
  │  6. PROMPT       Read prompts/prompt_NN_*.md  ~2,000 tok │
  │  7. CLARIFY/EMIT  Claude follows prompt contract         │
  │  8. REVIEW       specdev context review --step NN        │
  │     → structural (automated) + semantic pairs ~100-500   │
  │  9. VALIDATE     specdev validate + seed-lint + etc  0   │
  │ 10. REPORT       Summary + review verdict                │
  │                                                          │
  │  CONTEXT INPUT: ~4,500 tokens (steps 1-6 above)          │
  │  vs. reading all upstream specs raw: ~25,000+            │
  └─────────────────────────────────────────────────────────┘

3d. Token budget per step (full execution)

  Note: Section 3c shows context INPUT tokens only (~4,500). The full
  step execution budget below includes AI reasoning and review phases.

  Context prep (projected specs + seeds + prompt):    ~4,500
  Canon vocabulary (from A4b):                        ~200-400
  Clarify/Emit (AI reasoning + output):               ~2,000
  Review (structural, automated):                          0
  Review (completeness, ID-level comparison):         ~2,000
  Review (semantic, only for flagged items):           ~1,500
  Total full step execution:                         ~10,000
  vs. today (raw reads + no review):                 ~30,000+

3e. Tiered ingestion model

  Not all context is needed at the same depth. The extractor uses
  progressive depth based on the consumer's needs:

  Tier 0 — IDs only (~5% of tokens)
    Just the IDs and names from upstream specs.
    Used for: traceability binding, review ID coverage checks.

  Tier 1 — Summaries (~15% of tokens)
    IDs + one-line statements/descriptions.
    Used for: FR-to-capability mapping, scope checking.

  Tier 2 — Projected fields (~30% of tokens)
    Fields specified by scope resolver + extraction_paths.json.
    Used for: actual spec authoring (the default for extract).

  Tier 3 — Full spec (~100% of tokens)
    Complete JSON. Used for: ONLY when reviewing/auditing completeness
    or when --full flag is passed. Reserved for the review phase when
    Claude needs to verify nothing was dropped.

4. LOCKED DECISIONS
═══════════════════════════════════════════════════════════════════════════

Decisions below are final. Superseding information noted where applicable.

4a. trace_matrix auto-generation
  Always regenerate trace_matrix.json at the start of every context
  command. No staleness checks, no mtime comparisons. Spec directory is
  small; matrix generation is a local file walk. The file exists on disk
  but may be empty — scope_resolver must call `specdev matrix` first.

4b. step_order.json shape — downstream_consumers only
  step_order.json contains: version, _notes, policy, steps (22-item
  array), coverage_thresholds, downstream_consumers. required_spec_inputs,
  extraction_intent, and required_seed_inputs were removed in G4.
  required_inputs at runtime = inversion of downstream_consumers.

4c. x-consumed-by schema extension — REJECTED
  Adding x-consumed-by to schema properties would require schema updates
  whenever step dependencies change. Dependency information belongs in
  step_order.json, not in schema field annotations.

4d. context_schema_map.json — ELIMINATED
  No static config file needed. Payload descriptor is computed at runtime
  from schema files + trace_types.py.

4e. scope_resolver walks 2 graphs
  A3 walks trace graph (primary, for ID resolution) and step dependency
  graph (for input selection). Canon vocabulary delivery is handled
  separately by A4b. Canon reverse-index (cn:ID → [spec files]) is a
  documented extension point — buildable when a consumer needs sub-second
  reverse lookup, not pre-built.

4f. allOf resolution in A4
  Two concerns, handled separately:
  a) $ref resolution (URN → schema contents): Use
     SchemaRegistry.to_referencing_registry() — reuses the
     referencing.Registry the validation pipeline already depends on.
  b) allOf branch merging (union properties/required): Implement in the
     context package (~30 lines). The jsonschema validator does allOf
     merging internally during validation, but that logic is not exposed
     as a reusable API for property extraction.

4g. Boilerplate — dynamic from vc:core:step-base
  Boilerplate = vc:core:step-base property keys, loaded dynamically
  via SchemaRegistry.load('vc:core:step-base'). Currently 8 properties:
  $schema, id, owner, created_at, canonical_refs_used,
  canonical_proposals, canonical_conflicts, _migration_notes.
  Self-maintaining: new step-base fields are automatically boilerplate.

4h. Canon — third input type, schema-driven kind discovery
  18 of 19 step schemas have _ref fields referencing canon kinds (the
  exception is Step 13a completeness_assessment). Canon vocabulary is
  delivered via A4b using the 3-step mechanism:
  1. Identify canonicalRef fields ($ref target check, not _ref suffix)
  2. Resolve kind via INFERENCE_RULES (from canonical/autofix.py)
  3. Load canon/kinds/{kind}.json, extract id/preferred_label/definition/aliases

4i. Schema resolution authority
  schema_registry.json is the PRIMARY resolution path (SchemaRegistry in
  core/registry.py, used by validate.py and all linters). build_id_index()
  in json_utils.py is a parallel discovery mechanism for standalone use.
  A4 extractor uses SchemaRegistry, not build_id_index().

4j. Extractor/reviewer separation — no mode parameter
  Extractor (A4) always strips all step-base boilerplate. Agent gets
  vocabulary from A4b. Reviewer (A5) reads spec files directly (not via
  extractor) for structural + vocabulary consistency checks. Clean
  separation — no mode parameter needed.

4k. Prompt sanitization
  All prompts for Steps 05-16c had "Context To Ingest" sections removed.
  Context delivery is the skill's job, not the prompt's.

6. SEED TEMPLATE OPTIMIZATION (COMPLETE)

6a. Design decisions

D1: Pipeline Role Model — Seeds feed Steps 00-04 only. Steps 05+ derive
    from structured specs and use Clarify-Emit for gaps.
D2: Seed Ownership Boundary — seed_overview owns product intent,
    seed_tech_stack owns technical decisions. No overlap.
D3: Seeds Are Not System Specs — Seeds capture design intent accessible
    to non-developers.
D4: Drop seed_indexer and seed_reviewer — Redundant with existing
    pipeline. The seed_manifest system handles discovery, pipeline steps
    distill seeds, seed-lint validates references.
D5: [UNKNOWN] Protocol — Templates use [UNKNOWN: reason] as a sanctioned
    marker for genuinely unknown information.
D6: System-Type Agnostic Templates — Work for any software type.

6b. Hallucination vector cleanup

Three residual hallucination vectors found in all 16 prompts for steps
05-16c and corrected:

- Output Contract examples showed populated seed_refs → changed to []
- Self-Audit Gate said verify seed_refs list → changed to "seed_refs is []"
- spec/05_interface_contracts.json had stale seed_refs → cleared

All three signal layers are now aligned: seed_manifest only lists 00-04,
prompts have no seed references in 05-16c, output contracts show empty
arrays, schemas allow minItems: 0.

7. PHASE A — CONTEXT PACKAGE (CURRENT)
═══════════════════════════════════════════════════════════════════════════

7a. Build items

  A1. __init__.py — package init, public API exports
      Exports: get_step_structure, resolve_scope, extract_context,
      extract_canon, review_artifact, check_freshness. Re-exports from
      each submodule. Built last (after all other A-items are stable).

  A2. structure.py — step metadata + schema-derived canon kind affinity
      depends on: step_order.json, SchemaRegistry, canon/kinds/

      def get_step_structure(step_id, spec_dir, repo_root) -> dict

      Output format:
      {
        "step": "04",
        "required_inputs": [
          {"file": "00_charter.json",
           "keys": ["goals", "constraints", "in_scope", ...],
           "array_counts": {"goals": 5, "stakeholders": 3}},
          {"file": "01_capabilities.json",
           "keys": ["capabilities"],
           "array_counts": {"capabilities": 12}}
        ],
        "canon_kinds_needed": ["capability", "entity", "action", "role"],
        "seeds_required": ["seed-overview"],
        "output_schema_keys": ["functional_requirements",
                               "canonical_refs_used"]
      }

      required_inputs derived by inverting downstream_consumers:
        required_inputs(N) = [S for S in steps
                              if N in downstream_consumers[S]]
      array_counts: load each spec file, count array lengths.
      canon_kinds_needed: walk step schema _ref fields + INFERENCE_RULES.

  A3. scope_resolver.py — walks 2 graphs: trace + step dependency
      depends on: trace_matrix (regenerated on demand — A3 must call
                  `specdev matrix` first), step_order.json

      def resolve_scope(entry_id, spec_dir, repo_root) -> dict

      Output format:
      {
        "entry": "milestone-02",
        "resolved_ids": {
          "milestones": ["milestone-02"],
          "tasks": ["task-payment-flow", "task-payment-refund"],
          "frs": ["fr-payment-create", "fr-payment-refund"],
          "apis": ["api-payment-create", "api-payment-refund"],
          "fixtures": ["fix-payment-happy", "fix-payment-decline"],
          "nfrs": ["nfr-latency-p99"],
          "threats": ["threat-payment-injection"],
          "capabilities": ["cap-payments"],
          "invariants": ["inv-payment-positive-amount"]
        },
        "source_files": {
          "fr-payment-create": {
            "file": "spec/04_fr_list.json",
            "path": ".functional_requirements[3]"
          }
        }
      }

      Graph traversal algorithm:
      1. Regenerate trace_matrix: call specdev matrix programmatically
      2. Find the entry ID in trace_matrix rows or spec files
      3. Follow trace[].id edges: entry → linked IDs → their traces
      4. Collect all reachable IDs grouped by trace_type
      5. For each collected ID, record its source file + jq path
      Early steps (no entry_id): return "all" — extractor falls back
      to field-level projection.

      Extension point: canon reverse-index (cn:ID → specs), documented
      but not pre-built.

  A4. extractor.py — uses SchemaRegistry for schema access
      depends on: SchemaRegistry (from specdev_tools.core.registry),
                  scope_resolver (A3)

      def extract_context(step_id, spec_dir, repo_root,
                          entry_id=None) -> dict

      Output format:
      {
        "step": "16a",
        "scope": "milestone-02",
        "context": {
          "milestone": { /* just milestone-02 object */ },
          "functional_requirements": [
            { /* fr-payment-create full object */ },
            { /* fr-payment-refund full object */ }
          ],
          "apis": [ { /* api-payment-create full object */ } ],
          "nfrs": [ { /* nfr-latency-p99 full object */ } ],
          "invariants": [ { /* inv-payment-positive-amount */ } ]
        },
        "token_estimate": 730,
        "vs_full_read_estimate": 12400
      }

      $ref resolution: SchemaRegistry.to_referencing_registry()
      allOf merging: ~30 lines in context package (iterate branches,
                     union properties/required)
      Always strips step-base boilerplate (dynamic, from vc:core:step-base).
      NOTE: json_utils.py is outside specdev_tools package — NOT
      importable. allOf merge logic is implemented in context package.

      Scoping logic for traceable arrays:
        resolved_ids = scope_resolver.resolve_scope(entry_id)
        for item in array:
            if item[id_field] in resolved_ids[trace_type]:
                include item (stripped of boilerplate)

      Required-fields mode (fallback for non-traceable arrays or when
      no scope entry is provided):
        Tier 1 — use schema required[] array to build minimum viable
                 item. Strips optional fields (rationale, preconditions,
                 postconditions, links). ~30-40% reduction per item.
        Tier 2 — if item count > threshold (default 20), include
                 _context_note header and truncate. Escape hatch:
                 specdev context extract --step N --full to override.

      A4a. extraction_paths.json — hybrid cache of concrete jq paths
           per step/entry. Eliminates runtime path guessing for
           local/small-context models.

           How it works:
           1. extractor.py checks if extraction_paths.json exists and
              has an entry for the requested step
           2. If YES: use cached jq paths directly (no LLM needed)
           3. If NO (first invocation): extractor runs the payload
              discovery algorithm (section 7b) to determine which
              fields exist, then the /specdev-step skill prompts
              Claude to refine the paths based on the step's actual
              needs. Claude writes the paths to extraction_paths.json.
           4. Subsequent sessions reuse the cached paths.

           First-invocation trigger: the extractor checks
           extraction_paths.json[step_id]. If the key is missing or
           the file doesn't exist, it's a first invocation.

           Format:
           {
             "_meta": {
               "schema_hashes": {
                 "vc:04-fr-list": "sha256:abc123...",
                 "vc:00-charter": "sha256:def456..."
               },
               "generated_at": "2026-04-01T10:00:00Z"
             },
             "04": {
               "00_charter.json": [".goals", ".constraints",
                                   ".in_scope", ".out_of_scope"],
               "01_capabilities.json": [
                 ".capabilities[] | {capability_id, scope, owner}"
               ],
               "03_glossary.json": [
                 ".terms[] | {term, definition}"
               ]
             }
           }

           Staleness detection:
           - _meta.schema_hashes stores SHA-256 of each referenced
             step schema at cache generation time
           - On load, extractor computes current hashes and compares
           - If any hash differs: cache is stale for that step,
             paths are re-resolved on next invocation
           - If extraction_paths.json is missing entirely: all steps
             are "first invocation" — extractor uses the algorithm
             directly and the skill prompts Claude to populate cache

      A4b. canon_extractor — schema-driven kind discovery + extraction
           Step 1: walk step schema to find canonicalRef fields
                   ($ref target check, NOT _ref suffix alone)
                   ~15% of _ref fields (14 of 91) are non-canonicalRef
           Step 2: resolve kind via INFERENCE_RULES (promoted from
                   canonical/autofix.py lines 373-402 to shared constant)
           Step 3: load canon/kinds/{kind}.json, extract
                   id/preferred_label/definition/aliases
           ~40 tokens per entry, ~200-400 tokens per step total.

           def extract_canon(step_id, repo_root) -> dict

           Output format:
           {
             "step": "05",
             "canon_kinds": {
               "interface": [
                 {"id": "cn:core:interface:ask",
                  "preferred_label": "ask",
                  "definition": "...",
                  "aliases": ["ask"]}
               ],
               "entity": [],
               "event": [],
               "policy": [...]
             },
             "total_entries": 6,
             "token_estimate": 240
           }

           Nested _ref fields (inside array items): the schema walk
           recurses into items.properties for array-type properties.
           Multi-kind fields: INFERENCE_RULES maps each ref_field to
           one primary kind. If multiple rules match (via different
           source_field values), include all discovered kinds.

  A5. reviewer.py — two-pass review (structural + semantic pairs)

      def review_artifact(artifact_path, step_id, spec_dir,
                          repo_root, entry_id=None) -> ReviewResult

      Class definitions:

        class SourceRef:
            id: str              # e.g., "fr-payment-create"
            file: str            # e.g., "spec/04_fr_list.json"
            path: str            # e.g., ".functional_requirements[3].statement"
            text: str            # the actual text content

        class TargetRef:
            id: str              # e.g., "checklist-item-03"
            file: str            # e.g., "spec/16a_impl_planner.json"
            path: str            # e.g., ".plan.checklist[3].description"
            text: str            # the actual text content

        class ReviewPair:
            check_type: str      # faithfulness | acceptance_gap |
                                 # seed_distillation | quantifier_weakening |
                                 # scope_completeness
            description: str     # human-readable description of the check
            source: SourceRef
            target: TargetRef
            concern: str         # heuristic-generated hint for Claude

        class StructuralReview:
            upstream_coverage: dict  # {covered: [...], dropped: [...]}
            reverse_trace: dict      # {unjustified: [...], scope_creep: [...]}
            acceptance_criteria_coverage: dict  # {fr_id: {total, covered, missing}}

        class ReviewResult:
            structural: StructuralReview
            semantic_pairs: list[ReviewPair]
            verdict: str         # PASS | NEEDS_SEMANTIC_REVIEW | FAIL
            token_cost: dict     # {structural: 0, semantic_total: N}

      Pass 1 — Structural (automated, zero LLM tokens):
        - ID coverage: set comparison of upstream IDs vs emitted trace IDs
        - Reverse trace: output IDs not in resolved scope → scope creep
        - Acceptance criteria: match criterion_ids to checklist
          linked_test_expectations

      Pass 2 — Semantic pairs (auto-generated, Claude judges):
        5 check types:

        faithfulness — Does the emitted element preserve upstream meaning?
          Source: FR/capability statement text
          Target: corresponding checklist/API element text
          Heuristic: extract key nouns/verbs from source, check which are
          missing from target
          Example concern: "idempotency key and 2-second SLA missing"

        acceptance_gap — Is an acceptance criterion unmatched?
          Source: acceptance criterion text
          Target: nearest checklist item (by Jaccard similarity)
          Heuristic: if Jaccard < threshold, flag as gap
          Example concern: "No checklist item addresses idempotency"

        seed_distillation — Was a seed requirement faithfully captured?
          Source: seed doc excerpt (grep for domain terms matching scope)
          Target: spec element referencing the seed concept
          Heuristic: extract key terms (proper nouns, acronyms with
          qualifiers), check if target contains them
          Example concern: "PCI-DSS Level 1 → generic 'requirements'"

        quantifier_weakening — Was a specific metric replaced by vague language?
          Source: text with numbers/units (regex: \d+\s*(ms|s|%|MB|req/s))
          Target: corresponding target text
          Heuristic: check if target has fast|quick|acceptable|reasonable
          instead of the number
          Example concern: "'within 2 seconds' → 'acceptable latency'"

        scope_completeness — Are all expected output fields present?
          Source: extraction intent description
          Target: emitted artifact top-level keys
          Heuristic: expected fields from schema vs actual fields in output

      Reads canonical_refs_used directly from input specs (not via
      extractor) for vocabulary consistency checks.

      How Claude consumes semantic pairs (formatted by /specdev-step):
        SEMANTIC REVIEW — N pairs to evaluate:
        1. FAITHFULNESS: source_id → target_id
           Source: "..."   Target: "..."   Concern: "..."
           VERDICT: ___
        Claude reads ~50 tokens per pair and returns a verdict.

  A6. freshness.py — detect stale seed requirement indexes

      def check_freshness(spec_dir, repo_root) -> dict

      Mechanism:
        - seed_requirements.json (if it exists) stores source_hash:
          SHA-256 of each seed doc at extraction time
        - freshness.py reads current seed docs, computes current hash
        - Compares against stored hash
        - If different: seed has changed, index is stale

      Output format:
      {
        "seed-overview": {
          "indexed_hash": "sha256:abc123...",
          "current_hash": "sha256:def456...",
          "stale": true,
          "changed_sections": ["Performance", "Compliance"]
        }
      }

      When stale: emit warning W595 (or error if
      SPECDEV_WARNINGS_AS_ERRORS=1). The /specdev-step skill can then
      prompt Claude to re-index the changed seed sections.

      Note: This module is lightweight and only relevant if the project
      uses seed_requirements.json (the optional LLM-extracted seed index).
      If no seed_requirements.json exists, freshness.py returns
      {"status": "no_index"} and the pipeline continues normally.

7b. Payload discovery algorithm

  For A4 extractor.py:

  1. Read spec file's $schema URI
  2. Resolve via SchemaRegistry (the PRIMARY resolution path)
  3. Load schema via SchemaRegistry.load(uri) — returns raw dict
  4. Walk allOf branches:
     - allOf[0] = $ref to vc:core:step-base → boilerplate properties
     - allOf[1] = step-specific properties → payload
     - Some schemas have allOf[2] with if/then conditionals
       (02_system_sketch, 15_scaffold). These add conditional required
       fields, not new properties — safe to skip for payload discovery.
     allOf merging: iterate branches, union properties dicts, concatenate
     required arrays. $ref resolution via to_referencing_registry().
  5. Step-base properties = boilerplate (loaded dynamically)
  6. Remaining properties = payload
  7. For each array property in payload:
     - Inspect items.properties for a field ending in _id
     - Strip _id suffix → prefix string
     - Call normalize_trace_type(prefix), check against TRACE_TYPES
     - If in TRACE_TYPES: traceable array → scope via trace_matrix IDs
     - If not: non-traceable array → extract in required-fields mode
  8. Scalars and objects: always extracted fully

  Three payload categories (computed, not stored):
    traceable arrays    → scoped via trace_matrix IDs
    non-traceable arrays → extracted in required-fields mode
    scalars + objects   → always extracted fully

7c. Canon extraction mechanism

  The canonicalRef schema definition has kind as a free-form pattern
  (not constrained per-field). The intended kind is only in description
  strings, and naming conventions fail ~20% of the time (role_ref →
  kind is 'entity' in description, 'role' in canon data; unit_ref →
  kind is 'term' in description, 'unit' in canon data).

  Solution: INFERENCE_RULES from canonical/autofix.py (lines 373-402).
  This is the authoritative mapping — verified to match actual canon
  manifest entries and spec data. The schema descriptions are stale
  in some cases. This is a pre-existing toolkit inconsistency.

  B1. /specdev-step <NN> [--scope <entry-id>] — Full step orchestration

      File: .claude/skills/specdev-step.md

      Flow (10 steps, matching section 3c):
        1. ORIENT: run `specdev context structure --step NN`
           → Claude sees step metadata, required inputs, canon kinds
        2. SCOPE (if --scope provided):
           run `specdev context scope --entry <id>`
           → Claude gets resolved ID set
        3. EXTRACT: run `specdev context extract --step NN [--entry <id>]`
           → Claude gets scoped spec objects
        4. CANON: run `specdev context canon --step NN`
           → Claude gets relevant canon vocabulary entries
        5. SEEDS: Read seed docs listed in step_requirements (steps 00-04
           only; steps 05+ skip this)
        6. PROMPT: Read prompts/prompt_NN_*.md
        7. CLARIFY/EMIT: Claude follows the prompt contract:
           - Apply Self-Audit Gate (if confidence < 0.9 → output
             bulleted questions ONLY, stop and wait for answers)
           - When ready: write artifact to spec/NN_name.json
        8. REVIEW: run `specdev context review spec/NN_name.json --step NN`
           → If verdict is PASS: proceed to step 9
           → If verdict is NEEDS_SEMANTIC_REVIEW: present the semantic
             pairs to Claude for judgment. For each pair, Claude reads
             source text + target text + concern and returns ACCEPT or
             REJECT with rationale. If any REJECT: Claude fixes the
             artifact and re-runs review (max 2 iterations).
           → If verdict is FAIL: Claude reads the dropped/unjustified
             items, fixes the artifact, re-runs review (max 2 iterations).
        9. VALIDATE: run in parallel:
           - specdev validate spec/NN_name.json --repo-root .
           - specdev seed-lint spec --repo-root .
           - specdev canonical-integrity spec --repo-root .
           If any fail: Claude reads errors, fixes, re-validates (max 3).
       10. REPORT: Claude outputs summary:
           - What was emitted (file path, key counts)
           - Review verdict + any semantic pair judgments
           - Validation results (pass/fail per linter)
           - Next step recommendation

      Error handling:
        - Validation failure: fix and retry (max 3 attempts)
        - Review FAIL: fix and re-review (max 2 iterations)
        - Schema not found: check --repo-root, report error, stop
        - Step dependency missing: report which upstream step needs
          to be run first, stop

  B5. /specdev-pipeline <start-step> <end-step> [--scope <entry-id>]
      Full pipeline orchestration

      File: .claude/skills/specdev-pipeline.md

      Flow:
        1. Parse start-step and end-step from step_order.json steps array
        2. Build execution list: all steps from start to end (inclusive)
        3. For each step in order:

           e. If /specdev-step succeeds: log success, continue to next

      Error handling:
        - Upstream dependency missing: stop, report which step to run
        - Step failure: stop, report failure details from /specdev-step
        - Resume: re-run same command (skips completed steps)
        - --force: ignore existing artifacts, rebuild everything
