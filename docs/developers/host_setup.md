# Host setup

What a host repository gets from the toolkit, what it has to copy by hand, and how a release goes from preparation to production and, when it has to, to a rollback. The commands are in [reference.md](reference.md), the messages in [error-codes.md](error-codes.md) ("Merge and Release Gates"), the optional declarations file in [host_declarations.md](host_declarations.md). Every output quoted here was printed by a run on a scratch host that had the toolkit linked as `devspec_toolkit` (the worked example, `tests/fixtures/graph_example`, as the host's spec); the three things nobody has run are listed at the end.

## Run `update` once per clone, and commit what it wrote

`init` creates the directories, the toolkit submodule and the venv, then runs `specdev update spec --repo-root <toolkit> --install-only`; it installs nothing itself. An existing host runs the same command:

```bash
specdev update spec --repo-root ./devspec_toolkit --git-root . --install-only
```

It is idempotent: a second run prints `current (up to date)` for every piece and changes no byte. `--dry-run` prints `would_install` for each piece that has something to write and writes nothing. A plain `specdev update spec --repo-root ./devspec_toolkit` installs first and then does what it always did: re-stamp `spec/specdev_version`, or direct to `specdev align` when the schemas changed.

Two parts of the install live in the clone, not in the repository (below), so run `update` in **every clone**, and in a linked worktree for `.claude/settings.local.json`.

**Commit what `update` wrote before you run `specdev verify run`.** The files it installs (`.pre-commit-config.yaml`, `.github/workflows/`, `tools/`, `.claude/skills/` and `.claude/agents/`, `.gitignore`) belong to the code tree, the tree id that evidence records are tied to. Run on a copy: `release prep` ran the one binding and a second `release prep` said `1 already proven for this code tree`; after `update --install-only` (nothing committed yet) the next `release prep` said `1 binding(s) run ... 0 already proven`: the evidence was for another tree. What git ignores is outside the tree: `.git/`, `.specdev/` and the clone's `.claude/settings.local.json`.

## The seven pieces, in the order `update` runs them

`update` prints one line for each piece: `created`, `refreshed` (it rewrote what it owns), `current`, `drift` (it found something that is not what it would write and left it), `refused` (it could not do it; the other pieces went on) or `would_install`. Every warning is printed once (the W931 of a spec folder outside git too: one line, while the seven `refused` lines name the same reason), never changes the exit code and is never promoted. `--json` carries the same as `host_install`.

| Piece | What it writes, and where | In the repository? | What it never touches | `drift` and the flags |
|-------|---------------------------|--------------------|-----------------------|-----------------------|
| `pre-commit` | The toolkit's eight hooks (`dag-lint`, `extraction-intent-check`, `spec-check`, `seed-lint`, `canonical-lint`, `canon-schema-alignment`, `canonical-integrity`, `dependency-order-lint`) between the lines `# >>> specdev-managed` and `# <<< specdev-managed` of `.pre-commit-config.yaml` (the file is created from the template when absent; a config without toolkit hooks gets the block after its last local hook), then `<venv>/bin/pre-commit install` in the clone | The file yes; `.git/hooks/pre-commit` is per clone | Every line of the host's config outside the block | Hand-written toolkit hooks outside the block are left as they are: status `drift`, W930 for each hook that differs (with the template lines) and one for the hooks the config lacks. `--adopt` replaces them by one marked block at the position of the first of them, the host's other hooks kept. A damaged marker, invalid YAML or a CRLF file is `refused` (W931) |
| `merge-driver` | `merge.specdev-trace-lock.driver` (`<venv>/bin/specdev lock merge %O %A %B %P`) and `.name` in the clone's git config, and the line `spec/extras/trace.lock.json merge=specdev-trace-lock` in `.git/info/attributes` | **No: per clone.** Never a committed `.gitattributes`, which would change the code tree | `--global` git config, any other attribute | Re-run by hand: `specdev lock install-driver`. Without it git merges the lock as text and a conflict leaves markers in it (E760) |
| `workflows` | `.github/workflows/specdev-merge-check.yml`, from `templates/workflows/specdev-merge-check.yml`, first line `# specdev-managed: merge-check toolkit=<version>` | Yes | A host file of that name without the header | The file is rewritten whenever its text differs from the template (a line appended by hand was gone after the next `update`, status `refreshed`), so do not edit it. A same-name file without the header is left alone: `drift`, W930, also under `--adopt` (adopt covers hooks and wrappers, not workflows): move it aside and run `update` again. With no `setup_command` declared the "Host setup" step is left out and W935 is printed. It also reads the host's own workflows for retired commands (W932, below) and never rewrites them |
| `wrappers` | `tools/run_specdev.sh` (mode 0755) and `tools/ensure_venv.py`, rendered with the venv name | Yes | | A copy that equals the unrendered template (what `init` copies before the venv name is known) is refreshed silently. Any other edit is `drift` with W930 and a diff; `--adopt` rewrites it |
| `claude-links` | Relative symbolic links `.claude/skills/<name>` and `.claude/agents/<name>.md` into the toolkit's `.claude/` (5 skills and 12 agents on a run) | Yes (a link is a tracked file; it dangles if the submodule is removed) | A real file or folder at a link path: never replaced, also with the flag | A stale or broken link is `drift` with W930 naming `--force-claude`, which replaces it. A real file or folder is W930 too: move it aside and run `update` again (`--force-claude` does not clear it) |
| `ask-rules` | Ten rules in `permissions.ask` of `.claude/settings.local.json`: `Bash(specdev milestone sign-off *)`, `milestone defer *`, `release`, `release -*` and `verify attest *`, each also in the `./tools/run_specdev.sh` form | **No: per clone.** The installer adds `.claude/settings.local.json` to `.git/info/exclude` unless an ignore rule covers it already | Every other key and entry of the file; it adds no `allow` and writes no `settings.json` | A file that is not valid JSON, or whose `permissions` is not an object (`null` included), is `refused` (W931), byte for byte as it was, with the rules to merge by hand. |
| `gitignore` | The line `.specdev/` in `.gitignore`, once (an equivalent line counts) | Yes | Every other line | |

The ask rules are what makes the person's decisions a person's: Claude Code asks before it runs `specdev milestone sign-off`, `milestone defer`, `verify attest` and `release` (the cut). `release check`, `release prep` and `release rollback` are not asked.

### The venv name

`update` takes the venv from the interpreter that runs it: the folder name of `sys.prefix` when that folder lies directly under the host root, else `devspec_env`. The hook entries, the merge driver command and the wrappers are rendered with it, so `init --venv-name X` gives a wrapper that finds `X`: run with the interpreter of a `.venv` in the host, `update` wrote `VENV_DIR="${ROOT}/.venv"` into `tools/run_specdev.sh` and eight hook entries that start with `.venv/bin/python`.

### Retired commands in the host's own files

`update` reports, and never rewrites, a command that 1.2.0 removed when it stands in a workflow of the host (`.github/workflows/*.yml` without the toolkit's header) or in its `.pre-commit-config.yaml` outside the marked block. One W932 per line, each with what replaces it:

| Found | Replace by |
|-------|------------|
| `validate-all` | `specdev spec-check` (with `--merge` on a pull request) |
| `matrix` | `specdev coverage --by fr` for the FR view, `specdev trace --up\|--down <id>` for lineage |
| `forward-replay-check` | `specdev stale` for the pending replay, `specdev spec-check` for broken links |
| `completeness-check` | `specdev coverage` |
| `traceability-check` | `specdev spec-check` for the role-rule findings |
| a mention of `trace_matrix.json` | the file is no longer produced |

On the fixture host `w` (a hand-written `spec_validation.yml` with a `validate-all` step, a `matrix` step and a `strategy: matrix:` job) the run printed four warnings, for line 21 (`validate-all`), line 24 (`matrix` and `trace_matrix.json`) and line 29 (`trace_matrix.json`); the `strategy: matrix:` line was not reported.

### What `update` does not install

`spec/common/host_declarations.json`: copy `templates/host_declarations.host.json` and edit it (see [host_declarations.md](host_declarations.md)). `update` reads the file: the declared `setup_command` becomes the "Host setup" step of the merge-check workflow (W935 when it is absent), `release_tag_pattern` is what `release` needs (E911 without it) and `pin_sources` is what `spec-check --merge` compares. The three snippet templates below.

## The four workflow templates

All four are in `<toolkit>/templates/workflows/`. Only the first is installed; the other three are fragments that a person copies into the host's own deploy workflow, because `init` and `update` never touch deploy workflows.

| Template | Who puts it where | What it does |
|----------|-------------------|--------------|
| `specdev-merge-check.yml` | `update` writes it to `.github/workflows/specdev-merge-check.yml` | Job `merge-check` (`contents: read`, checkout with `fetch-depth: 0` and submodules): the governance check of the pull request title, then `spec-check spec ... --merge --base-ref "origin/$BASE"` on a pull request and `--merge --base-ref "$BEFORE"` on a push to the default branch, plain `spec-check` on the other runs. Job `release-prep` (`contents: write`): on a pull request from a branch of this repository named `release-prep/...`, `specdev release prep`, then it commits the evidence under `spec/extras/verification` to that branch |
| `specdev-step.snippet.yml` | A person copies it into a job of the host's own pull-request test workflow, for a host that wants the merge gate there instead of using the installed workflow | One step, `spec-check ... --merge --base-ref "origin/$BASE"`; the job needs `contents: read`, a checkout with `fetch-depth: 0` and `submodules: recursive`, and the toolkit on `PATH` |
| `deploy-preamble.snippet.yml` | A person copies the list of steps into the host's deploy workflow, ahead of the host's own deploy steps | The order is fixed (below) |
| `evidence-pr.snippet.yml` | A person copies it after the post-deploy steps | Opens a pull request that carries the evidence the deploy wrote |

**The order of the deploy preamble**, and what stops the job: (1) `specdev third-party check --installed tp-example=1.0.0 --env "$SPECDEV_ENV" --tag "$TAG"`, which exits 1 (E339) when an installed version is not the pin; (2) `specdev release check --stage prod --tag "$TAG"`, only when `SPECDEV_ENV` is `prod`, which exits 1 when the production gate blocks; (3) the host's own deploy steps, at the line `# --- the host's own deploy steps go here ---`; (4) `specdev verify run --all --stage "$SPECDEV_ENV" --only-stage`; (5) `specdev plan record --at-deploy ITEM/ACTION --env "$SPECDEV_ENV" --tag "$TAG"`. A failing step before the deploy stops the job before the deploy. Edit `tp-example=1.0.0` to the third parties and versions this deploy installs, and `ITEM/ACTION` to the `at_deploy` actions of the plan (`PWRESET_CONFIRM_EXPIRED_01/a03` in the worked example).

**What the deploy job needs.** Job-level `env:` values `SPECDEV_ENV` (`staging` or `prod`) and `TAG` (for example `${{ inputs.tag }}`); a checkout of the dispatch ref with `fetch-depth: 0` and submodules (the default branch head, so that merged staging evidence is present; a host that builds from the tag checks the tag out separately); the toolkit installed with its venv `bin` on `PATH`; permissions `contents: write` and `pull-requests: write` for the evidence pull request.

**Variables and secrets, all optional.** Secret `SPECDEV_CHECKOUT_TOKEN`: a token that can read private submodules (the job's own token is the fallback). Repository variable `SPECDEV_RELEASE_PREP_PREFIX`: the branch prefix of a release-prep pull request (default `release-prep/`). A spec folder other than `./spec` or a toolkit path other than `./devspec_toolkit` is rewritten by the installer in the merge-check workflow; in the snippets it is an edit by hand. The merge-check workflow is not assumed to be a required check: a host may require the `merge-check` job on its branches; nothing in the toolkit depends on it.

**A pull request's text never reaches a shell by interpolation.** The title, the base ref and the head ref are passed as `env:` values (`PR_TITLE`, `BASE`, `HEAD_REF`) and read as `"$PR_TITLE"`; no `${{ }}` stands inside a `run:` block of a template. Keep it so in your copies.

**What GitHub does with the evidence.** A push or a pull request made with the job's own `GITHUB_TOKEN` starts no workflow run, and a pull request that token opens needs an approval before workflows run on it; whether Actions may open pull requests at all is a repository setting (Settings, Actions, General). No template changes a setting. A pull request from a fork gets a read-only token, so `release-prep` does not run on it.

**Manual deploys.** A deploy that nobody ran through the preamble writes no deploy evidence: the staging and production at-deploy records and the stage's verification runs exist only if the commands ran. A person who carried an action out by hand records it with `specdev verify attest ITEM/ACTION --env staging|prod`, which writes the same record as `plan record --at-deploy`. The next release asks for these records (E920).

**Two runs of the bound commands.** The `merge-check` job runs the dev and CI bindings of the milestones the branch closes (E901), and the `release-prep` job runs the dev and CI bindings of the release again to record their evidence; both run next to each other, not one after the other. A host that also runs its own test suite in a workflow of its own runs those commands a third time. Nothing deduplicates them.

## A release from prep to rollback

The sequence the integration test `tests/integration/test_m9_release_flow.py` runs, in a person's words, with the commands as run on a scratch host (the worked example made release-ready: every obligation parked, one NFR waiting for staging proof, one at-deploy action for staging and prod). The Git steps are plain Git.

1. **Prepare, on a branch.** `git checkout -b release-prep/v1.0.0`, then `specdev release prep`. It printed `release prep: 1 binding(s) run, 1 passed, 0 failed; 0 already proven for this code tree`, `PASS ver-password-reset-expired-token (evd-password-reset-expired-token-ci)`, `the evidence is written under spec/extras/verification/ and not committed: commit it through the branch` and `left for the release gate: nothing, once the evidence is committed (the cut refuses a tree that is not clean, E910)`. A second run ran nothing (`1 already proven`) and, with nothing written, printed `left for the release gate: nothing blocks the release`. The only new file was `spec/extras/verification/evd-password-reset-expired-token-ci.json`. The installed workflow does this step for a `release-prep/` pull request.
2. **Commit the evidence and merge.** Commit, open the pull request, let the `merge-check` job run `spec-check --merge`, merge. `specdev status` then printed, under "Production verification", `previous release: none` and `state: none`.
3. **The cut.** On the default branch, with a clean tree: `specdev release --tag v1.0.0 --message "first release"`. It printed `release v1.0.0: annotated tag created on <commit> (first release)`, `release gate: 0 error(s), 8 warning(s), 27 listed (not blocking)` and `the tag is not pushed: pushing it starts the deploy; push it yourself (`git push <remote> v1.0.0`)`. The tag was annotated (`git cat-file -t v1.0.0` is `tag`), on `HEAD`, and nothing else changed (`git status` empty). A person pushes the tag; the command never does. The ask rule that `update` installed makes Claude Code ask before this command runs (not run here, see the last section).
4. **The staging job.** The host's deploy workflow runs the preamble with `SPECDEV_ENV=staging` and `TAG=v1.0.0`: `third-party check --installed tp-argon2=0.41.1 --env staging --tag v1.0.0` (`tp-argon2: installed 0.41.1 is the pin; recorded extras/verification/evd-argon2-staging-install.json`), the deploy, `verify run --all --stage staging --only-stage` (`PASS ver-latency at staging`), `plan record --at-deploy PWRESET_CONFIRM_EXPIRED_01/a03 --env staging --tag v1.0.0` (`recorded dep-0001: ... done at staging`). Three files were new (`dep-0001.json`, the install record, the staging evidence). The evidence pull request carries them; merge it.
5. **The production gate.** `specdev release check --stage prod --tag v1.0.0` printed `release check --stage prod v1.0.0 (commit ..., code tree ...): passes` (exit 0). It reads the spec as it was at the tag, so a later spec edit does not change the answer, and the evidence from the checkout, so the staging evidence merged after the tag counts. With the staging evidence missing it printed `E347 ... run `specdev verify run ver-latency --stage staging``, exit 1. `specdev status` at this point printed `state: not verified (released, awaiting production proof)` and the E920 line for the prod record.
6. **Production evidence.** The prod job runs the same preamble with `SPECDEV_ENV=prod`: `third-party check ... --env prod`, the gate of step 5, the deploy, `verify run --all --stage prod --only-stage` (`0 run, 0 passed, 0 failed`: this host binds nothing at `prod`), `plan record --at-deploy ... --env prod --tag v1.0.0` (`recorded dep-0002: ... done at prod`), the evidence pull request, merge. `specdev status` then printed `state: verified in production`. That state asks only for what the release closed: the production proof of what waited for it and the at-deploy records of the milestones it closed. A release that closed no milestone owes no at-deploy record and reads `verified in production` without any deploy (a plain release-ready host: cut `v1.0.0`, commit, and `status` printed `previous release: v1.0.0`, `state: verified in production`).
7. **The next release.** `specdev release --tag v1.1.0` printed `release v1.1.0: annotated tag created on ...`. The previous release is the nearest ancestor of `HEAD` whose tag matches the pattern (a tag on `HEAD` itself is not one); its spec is read at its own commit.
8. **When the previous release was not verified.** With the prod record removed, the cut printed `release v1.1.0: not tagged; the release gate found 1 error(s), ...` and `E920 the previous release v1.0.0 is not verified in production: at-deploy action PWRESET_CONFIRM_EXPIRED_01/a03 has no done record for prod; verify it, or waive it with `specdev release rollback v1.0.0 --reason "..."``; no tag, nothing written.
9. **A rollback.** `specdev release rollback v1.0.0 --reason "v1.0.0 never reached production"` printed `recorded the rollback of v1.0.0 (.../spec/extras/releases/rollback-v1.0.0.json): its production verification is waived for the next release check` and `the file is written, not committed: commit it through the normal branch`. Until it is committed the cut says E910 (`the working tree is not clean (1 path(s): spec/extras/releases/rollback-v1.0.0.json)`); after the commit it tagged, and `status` printed `state: rollback recorded`. A second rollback of the same tag is E927, a blank reason E926, an unknown tag E925.

## What nobody has verified

- The four templates on a live GitHub runner: they are parsed as YAML, every `specdev` line in them is parsed by the real command parser and run in order on a scratch host, but no workflow ran. `vars` inside a job `if` (the `release-prep` condition) is unverified, and so are the GitHub behaviours described above (the token that starts no run, the approval of a pull request a token opens, the repository setting).
- Whether Claude Code reads `.claude/settings.local.json` in each linked worktree, and a real Claude Code prompt on one of the ten rules.
- A real tag push, a real deploy, and the installer's refusals that need a failing environment (a failed `pre-commit install`, an unwritable file, a link that cannot be made). `init` was run end to end only with the venv step replaced.
