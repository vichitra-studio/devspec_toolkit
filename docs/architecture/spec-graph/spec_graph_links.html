Spec graph links, step by step

What x-node and x-link are, how one spec links to another, and why some links stay inside a single spec. One small example, the password reset, runs through the whole page.

Three pieces

The rules about links live in one place, the data lives in another, and a tool reads both.

The rulebook Step schemas (toolkit)

Each step's JSON schema carries two extra annotations: x-node says "items here are nodes"; x-link says "this field links to these kinds". Hosts never edit these.

The data Spec files (host repo)

Each spec node stores its own id and, in fields named after a verb, the ids of the nodes it depends on. Nothing else: no paths, no copies of text.

The tool specdev

Reads the rulebook to know where nodes live and what each link may point at, then checks every link in the data and tracks changes in the trace lock.

rulebook+data→specdev checks and tracks

x-node: "the items in this list are nodes"

"third_parties": {
  "type": "array",
  "x-node": {
    "kind": "third-party",       ①
    "id": "third_party_id",      ②
    "role": "context",           ③
    "contract": ["name", "pin"]  ④
  }
}
  1. kind names what sort of node this is. The tool builds one registry of every kind, so it can find any node by id.
  2. id names the field holding the node's id. Ids are unique across the whole spec.
  3. role picks the rule the node must meet: an obligation must be built and proven, a verifier must run, context needs only to be used.
  4. contract lists the fields whose change matters. Change one of them and every node that depends on this one becomes suspect.

x-link: "this field links to these kinds"

"connects_to": {
  "type": "array",
  "items": { "$ref": "vc:core:atoms#kebabId" },
  "x-link": {
    "kinds": ["component", "third-party"],  ①
    "required": true,                         ②
    "built": false                            ③
  }
}
  1. kinds: the ids in this field must be nodes of these kinds. A typo, a missing node or a wrong kind is an error.
  2. required: whether the field may be empty.
  3. built: whether building the node at this end counts toward building the node it points at.

The relation is the field's name, so it is never written twice. In the spec file the same field is just ids:

{ "connection_id": "conn-identity-to-mailrelay",
  "derives_from": ["identity-service"],
  "connects_to":  ["tp-mailrelay"] }

Linking across specs

The later node stores the link.

The API at step 05 stores derives_from: ["fr-password-reset"]. The FR at step 04 stores nothing about the API. The tool works out "who uses this FR" by reading links backwards.

Links point back, never forward.

A node may link only to a node in an earlier step or its own step. A step-04 FR can never link to a step-05 API, because that API doesn't exist yet when the FR is written.

Only the id is stored.

No file path, no line number, no copy of the target's text. The tool finds the node through the kind registry.

The tool remembers what the author saw.

For every link, the trace lock keeps a hash of the target as it was when the link was last checked. If the target changes, the link and everything below it become suspect until someone re-checks them.

Why some links stay inside one spec

Some relationships are decided within a single step. If there were no link, the relation would live only in prose. Then the tool could not check it, and a change on one side would never reach the other.

Step 02 · system sketch
connection → identity-service, tp-mailrelay

An architecture arrow joins two boxes drawn in the same sketch. If MailRelay's pin changes, the connection, and the threats and NFRs on it, are re-checked.

Step 04 · FRs
fr-password-reset depends_on fr-send-email

A reset needs the email feature. Without the link, a change to how emails are sent would never flag the reset flow.

Step 00 · charter
risk derives_from assumption

A risk is often "what if this assumption is false". Linking them means a changed assumption flags the risk.

Step 14 · roadmap
task depends_on task

One task must finish before another starts. The tool orders the work from these links and catches cycles.

Same-step links follow the same rules as any other link: declared in the schema, ids only, checked, and tracked in the lock. A loop among them, such as A depends on B and B depends on A, is an error.
